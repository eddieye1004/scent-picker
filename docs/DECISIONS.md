# 决策记录

每条都是**已拍板**的，不是待选方案。左侧是当时的选项，右侧是结果与理由。

---

## D01 · 数据规模：200 瓶，不做全量

**选项**：抓全量（源站数千瓶）/ 抓 200 瓶

**决定**：200 瓶。

**理由**：全量抓取意味着要处理缺失字段、重复条目、异常香调列表的时间成本，而这个项目的核心风险不在数据量，在**推荐逻辑能不能讲清道理**。200 瓶足以覆盖 6 大家族 × 13 个源家族，足以验证逻辑。数据管线的 `build-data.js` 保留着，扩到 500 只是改一个常量加一轮清洗。

**代价**：用户心里已经有的那瓶大概率不在库里。这点写进了 README 的"已知局限"。

## D02 · 应用层只用结构化事实字段；上游数据集原件随仓库分发（已修订）

> **修订记录（2026-10-28）**：本条初版写的是"原始数据不入公开仓库"，那是在**误以为 `perfumes.jsonl` 是我们自己抓的**前提下写的。核查后前提被推翻——它是上游主动以 CC BY 4.0 公开发布、供再分发的数据集文件本身（见 COMPLIANCE.md 第一节）。原文与仓库实际状态矛盾，故修订。修订依据：`git hash-object` 本机副本 = `8c745960a9bd7796bce68518e82f19ff17eaaaf1`，与上游 `perfumes.jsonl` 的 git blob sha 逐字节一致。

**选项**：把上游数据集原件一起入库 / 只提交清洗后的结构化字段

**决定**：两者都做，但**分工明确**——

| 位置 | 内容 | 用途 |
|---|---|---|
| `data/source/perfumes.upstream.jsonl` | 上游 CC BY 4.0 发布的原件（1.1 MB / 1,320 行，含 `description` 原文） | 可复现性：`build-data.js` 离线即可重建，且保留上游原貌便于比对 |
| `data/perfumes.json` | 清洗后的 200 瓶结构化事实（**不含 `description`**） | 应用层唯一数据源，前端只读这份 |

**理由**：许可允许再分发，不等于应用层需要搬运全部字段。

- 事实字段（香调名、品牌、家族）不受版权保护，直接用于应用层
- `description` 是 Scento 撰写的独创性文字。**应用层不呈现它**——不是因为不能（CC BY 4.0 允许），而是因为第一人称问卷的推荐理由必须能反推到用户自己的答案，第三方文案做不到
- 原件保留在 `data/source/` 且已署名，满足 CC BY 4.0 的 Attribution 与 Indicate Changes 两项义务（详见 COMPLIANCE.md）

**代价**：仓库多 1.1 MB。换来的是任何人 clone 后 `node scripts/build-data.js` 就能复现 `data/perfumes.json`，不需要联网、不需要信任我们的抓取过程。

## D03 · 大模型只润色不参与选品

**选项**：让模型直接看用户答案推荐 / 规则引擎选品 + 模型生成理由

**决定**：规则引擎选品。理由文案也用模板拼接，**运行时完全不调模型**。

**理由**三条：

1. **稳定性**：同一个问题问两次，模型可能给两瓶不同的香。推荐器不可复现是致命的。
2. **可验证性**：规则引擎的每一条理由都能反查到"你第 2 题选了约会 → 这瓶时段含 evening"。模型的理由是生成的，可能是幻觉（"这瓶有香草"而实际没有）。
3. **安全性**：纯静态站，前端调模型 API 意味着 API Key 必须暴露在浏览器里。

**代价**：理由文案是模板化的，句式重复度较高。缓解办法是每条理由绑定**具体的命中项**（"含你点名的佛手柑"而不是"符合你的喜好"），让重复的句子里填的是不同的证据。

## D04 · 家族体系：源站 13 类映射到面向用户的 6 类

**选项**：直接用源站家族名 / 自建一套 / 映射

**决定**：映射，`sourceFamilyMap` 手工表。

**理由**：源站的家族名（`Orchard Fruit`、`Velvet Sweet`、`Green Leaf`）对新手是黑话。但另起一套会让数据失去可追溯性。映射表让两边都保留：

```
用户看到的：美食调 / 木质调 / 花香调 / 柑橘调 / 清新调 / 琥珀调
数据保留的：Velvet Sweet / Woody / Floral / Citrus / Fresh / Amber & Resin
```

**代价**：映射有主观成分。`Orchard Fruit` 被归到花香调而非果香调，是因为源站这个家族下的代表香（Aventus）实际偏果香木质——这直接导致了 D08 的锚点层修复。

## D05 · 前端零构建：原生 ES Module

**选项**：React + Vite / 原生

**决定**：原生，无 `package.json`，无 `node_modules`。

**理由**：目标用户是"有基础开发能力的新手"。第一次 clone 下来如果先要 `npm install` 然后遇到 node 版本冲突，项目就死在这一步了。现在 `node server.js` 就能跑。

**代价**：没有组件化，`app.js` 单文件约 400 行。这个体量下可接受；再大就该引入构建了。

## D06 · 三个独立测试脚本，不用测试框架

**选项**：Vitest / Jest / 手写脚本

**决定**：手写，零依赖。

**理由**：与 D05 同理。而且这三个脚本的分工比框架更清楚——它们不是单元测试，是**三种不同粒度的体检**：

- `test-scoring.mjs`：穷举所有答案组合（105 项），验引擎不崩、结果幂等、讨厌项生效
- `test-render.mjs`：DOM 桩跑完整流程，验文案与三调渲染（25 项）
- `qa-data.mjs`：数据层体检，验结构、唯一性、家族覆盖、可溯源

**代价**：没有 watch 模式，每次改完手动跑三行命令。

## D07 · 视觉验证：从"完全不做"改为"用本机 Edge 无头"

**最初尝试**：puppeteer / playwright 截图对比

**结果**：本机沙箱拒绝。它们自带的 Chromium 启动时 mojo IPC 通道被策略拦截，进程起不来。

**替代方案（第一版）**：实现了一个最小 DOM 桩（`el` / `appendChild` / `textContent` / `dataset`），让 `app.js` 真的执行完整四步流程，再对其产出的文本断言。

**这条的边界必须说清**：它证明**逻辑与文案正确**，不证明**CSS 视觉表现**。布局错位、字体溢出、移动端塌陷这类问题它一个都抓不到。README 里因此留了一条"人工在真实浏览器看一遍"。

**后续更正（已实测）**：上面那句"本机无法截图"是**错的，只对 puppeteer/playwright 成立**。本机装了 Edge，直接用它的 `--headless=new --screenshot` 是可行的：

```
msedge.exe --headless=new --disable-gpu --no-sandbox ^
  --user-data-dir=<临时目录> --virtual-time-budget=7000 ^
  --window-size=1280,1000 --screenshot=shot.png ^
  http://127.0.0.1:8123/
```

配合 `--dump-dom` 还能拿到真实渲染后的 DOM（本文件里"结果页文本"的核查就是这么做的）。
**教训**：把"某个工具被沙箱拦了"记成"这件事做不到"是偷懒的归因。换一个已装在本机的浏览器就绕开了——先穷举本机已有的可执行文件，再下"做不到"的结论。

**残留局限**：静态截图看不出交互态（hover/focus）、也说不了移动端真机上的滚动与手势表现。

## D08 · 加"情绪锚点香调"层（本版最重要的一次修复）

**问题**：初版只按家族向量打分。实测"清冷 + 约会 + 强度 2"时，**Creed Aventus 排第一**（80.6 分）。

为什么错：Aventus 被源站标成以 floral 为主的 `Orchard Fruit`，家族向量与"清冷"不冲突。但"清冷"在气味语义上要的是鸢尾、紫罗兰、柏树那种**冷感**，而 Aventus 是明亮的果香木质。家族层太粗，区分不出来。

**修复**：在家族层之上加一层**情绪锚点**——每种情绪对应 5 个锚点香调：

| 情绪 | 锚点香调 |
|---|---|
| 清冷 | 鸢尾、紫罗兰、柏树、香根草、焚香 |
| 温暖 | 香草、琥珀、零陵香豆、肉桂、檀香 |
| 干净 | 皂感、白麝香、棉花、醛、铃兰 |
| 神秘 | 乳香、没药、皮革、广藿香、藏红花 |
| 明亮 | 佛手柑、柠檬、橙花、葡萄柚、黑加仑 |
| 慵懒 | 麝香、椰子、无花果、零陵香豆、檀香 |

权重 22 分（仅次于家族 52 分）。修复后同一查询的第一位变成 **Byredo Gypsy Water**（含鸢尾 + 焚香），语义才对齐。

**教训**：**粗粒度分类永远会漏掉语义。** 当用户用感受性词汇（"清冷"）提问时，必须有一层能直接落在具体材料上的映射，否则分类体系再整齐也是错的。

## D09 · 源家族 + 品牌双重去重（前三名互不重复）

**问题**：初版前三名可能全是 `Velvet Sweet`，对用户毫无参考价值——三瓶闻起来是同一个方向。

**第一版修复**：排名阶段做贪心去重，已出场的源家族在后续候选中降权。

**第二次修复（2026-10-28 实测发现第一版不够）**：只用家族去重仍会被单一品牌垄断。样本里 Byredo 有 9 瓶、横跨 4 个源家族，家族层去重拦不住——它们的源家族确实不同。

实测（复现旧逻辑，遍历 6 情绪 × 5 场合 × 6 个点名香调 = 180 组）：
- 不带点名香调：30 组里 **2 组**品牌重复（`cold/date` 出 Byredo + Zoologist + Byredo）。
- 带点名香调：180 组里 **18 组**品牌重复，最差的一组 `cold/date/Bergamot` 是 **Byredo + Byredo + Byredo** —— 三瓶同一个牌子。

走「点一个喜欢的香调」这条路时必然触发，不是极端案例。

**修复**：品牌与家族**同时**去重，分三轮放宽：
1. 首轮要求家族不同 **且** 品牌不同；
2. 不够数则放宽到"品牌不同"（允许同家族）；
3. 再不够则彻底放宽，保证一定凑满 topN。

**验证**：`scripts/test-scoring.mjs` 的 T11 遍历 30 组无香调组合，断言三瓶品牌互异；修复后 30/30 通过，测试总数 105 → 106。

**理由**：推荐 3 瓶的目的不是"把最像的都给你"，是**给你三个可以对比着试的方向**。同品牌三连会直接摧毁这个目的——而不只是"看起来不够多样"。

## D11 · 部署目标：GitHub Pages（纯静态）

**决定**：纯静态，无后端。

**理由**：推荐逻辑全在客户端（D03），没有需要保护的服务端逻辑，也没有用户数据要存。静态托管意味着**零成本、零运维、不会挂**。

**代价**：数据更新需要重新构建并提交。200 瓶的量级下，这反而是优点——每次数据变更都有 git 记录。

## D12 · 香调匹配改为「按词匹配 + 显式别名」

**决定**：不用双向子串（`pn.includes(n) || n.includes(pn)`），改为把香调名切成词，按词边界匹配，并以 `taxonomy.noteIndex.entries[].aliases` 显式补充同义写法。匹配逻辑集中在 `src/notes.js`。

**理由**：子串匹配会造成用户能感知到的错判。实测 200 瓶数据：
- `晚香玉 tuberose` 声称命中 **72 瓶**，实际只有 **9 瓶** —— 因为 `Tuberose` 里含 `rose`，把玫瑰全吃进来了。
- `玫瑰 rose` 声称命中 **85 瓶**，实际 **65 瓶** —— 误吃 `Tuberose` / `Rosemary` / `Rosewood` / `Pomarose` / `Rosehip`。
- 连带 `铃兰 lily of the valley`（原被 `lily` 子串拉进 5 瓶）、`檀木 sandalwood`（原靠 `sandalwood.includes('wood')` 凑）同样受影响。

**代价**：需要维护 `aliases` 表。当前只补了 6 条（雪松/海水/绿茶/无花果叶/橙花/苦橙叶），其余靠按词匹配已能覆盖。新数据和失败样本出现时要继续补。

## D13 · 死选项按命中数过滤，不上屏

**决定**：第 4 步的香调 chip 只渲染「在当前 200 瓶样本里至少命中 1 瓶」的条目（`src/notes.js` 的 `usableEntries()`），计数由数据算出，不写死。

**理由**：`可可 cocoa` 在 200 瓶里出现 **0 次**。用户勾了它，界面给了勾选反馈，但打分环节没有任何一瓶能命中——等于骗了一次点击，且用户无从知道为什么没效果。

**代价**：`usableEntries()` 每次要扫 200×40。已在 `app.js` 里按数据对象引用缓存结果，重渲染不重算。数据换掉时缓存自动失效。

**实测**：40 → 39，隐藏 1 个（可可）。首屏 16 个仍覆盖全部 6 个家族。

**未做**：没有反过来「扩充香调到数据里」（比如把 cocoa 加到某些美食调香水），因为那是改数据，超出修 UI 的范围。

## D14 · 前两步改成 HUD 圆盘，但命中区仍是真实 button

**决定**：第 1 步（情绪，6 项）与第 2 步（场合，5 项）从纵向列表改成环形圆盘选择器。**扇形用 SVG 画，但可点区域是绝对定位的真实 `<button>`**。

**理由**：用户明确要「钢铁侠操控台那种圆盘」。但纯 SVG 交互有三个硬伤：480×480 坐标系里做命中测试拿不到 44px 触控保护；键盘 Tab 进不去；`role="radio"` 语义没法挂在 `<path>` 上。所以形状归 SVG，语义归 HTML。

**做法**：
- `annulusPath(rOut, rIn, a0, a1)` 拼环形扇区路径，`gapDeg: 1.6` 留出缝
- 第一个扇区正对 12 点（`startBase = -90 - half`），读起来像仪表盘
- 标签落 `midR = (rIn + rOut) / 2` 极坐标点，转百分比定位，保证不出圆
- 盘心 `.disc-hub` 34% 直径，hover/focus 时显示该项说明；离开后回退到已选项
- roving tabindex：选中项或首项 `0`，其余 `-1`；方向键移动焦点时同步搬 `tabindex`，否则 Tab 离开再回来会跳回第 0 项（实测过这个 bug）

**代价**：`scripts/test-render.mjs` 的极简 DOM 桩要补三样能力才测得动——`createElementNS`、`setAttribute('class')` 同步 `classList`、`tag.class` / `[attr="v"]` / `.a.b` 选择器。补之前 4 条断言全假失败。

**实测**（真实浏览器）：圆盘 560×560、盘心 190.4×190.4（=34%）、扇区最小 56×59.2（>=44）、6 个标签零溢出零重叠、无横向滚动条。

## D15 · 控件边界单独用 `--edge`，不再复用 `--line`

**决定**：`:root` 新增 `--edge: #42688f`（对 `--bg` 3.39 : 1），`.sector-shape` 的 `stroke` 从 `--line` 换成 `--edge`。`--line` 降级为「纯装饰分隔线」。

**理由**：WCAG 1.4.11 要求 UI 组件边界 >= 3 : 1。实测 `--line #21324a` 只有 **1.52 : 1**，拿它画扇形描边等于没画——用户看不出哪里能点。而纯填充色无论怎么提亮都到不了 3（`#1e3752` 也只有 1.62），深色主题下填充必然贴近底色，只能靠描边。

**代价**：多一个颜色变量。`scripts/test-contrast.mjs` 加了一组非文字对比度检查（PASS 20 → 25），并加了一条反向自检：`--line` 必须真的低于 3，否则说明「装饰色当边框用」这个错它抓不到。

## D16 · 库容从 200 扩到 400，且抽样按「家族 + 子家族」双配额

**决定**：`scripts/build-data.js` 加 `--limit 400 --sub-quota 6` 两个参数。家族保底之后再做一轮子家族保底，每个子家族至少 6 瓶。

**理由**：200 瓶时只按家族配额抽样，导致 5 个子家族几乎没有货——实测 `gourmand/boozy` 3 瓶、`gourmand/coffee-cocoa` 4 瓶、`fresh/green` 4 瓶、`fresh/tea` 6 瓶。这些子家族在第二层轮盘里是可选项，点进去只有 3 瓶，等于假选项。而全量 1,228 行里最少的子家族也有 24 行，说明不是数据不够，是抽样不均衡。

**实测**：模拟不同库容与保底值，`LIMIT=300 + SUB_QUOTA=6` 就已消除全部薄扇区；取 400 是因为用户要求「多加 200 瓶」。重建后 32 个子家族最薄 7 瓶（`coffee-cocoa`），其余 24 个都在 10 瓶以上。

**代价**：`perfumes.json` 从 261 KB 涨到约 500 KB。仍是单个静态文件，前端一次 fetch 即可，不值得为此上分页或数据库。

## D17 · 香调索引从 40 条补到 56 条，补的是空子家族而不是「热门的」

**决定**：新增 16 个香材，让 32 个子家族**全部**有香材挂靠。顺序是先补 0 香材的空子家族（`floral/soliflore`、`woody/woody-aromatic`、`gourmand/fruity-gourmand`），再补货量最薄的。

**理由**：点进一个子家族却看不到任何香材，和之前修掉的「死 chip」是同一类错误——界面说了有，实际是空的。补什么不能凭印象：先在上游 1,228 行里跑真实 surface 词频，只收命中数够的。

**实测剔除名单**（写在这里是为了下次不要重复试）：`narcissus` `banana` `black tea` `white tea` `earl grey` `mate` `chai` `whiskey` `brandy` `wine` `bourbon` `sake` `martini` `gin` `nettle` `moss` `bay leaf` `eucalyptus` —— 这些在数据里 **0 命中**，绝不能写进 taxonomy。

**代价**：`noteIndex` 从 40 条到 56 条，「展开全部」的清单变长。已用「按家族轮流取样」的 PEEK 逻辑消化，首屏仍只露 16 个。

## D18 · 扇形本体自己绑定点击，不只依赖扇区上的标签按钮

**决定**：每个 `<g class="sector-g">` 直接挂 `click` / `mouseenter` / `mouseleave`，行为与标签按钮完全一致（同一份 `pick.current` 状态、同一套 `setOn`、同一个 `onPick`）。

**理由**：扇区是半径 104–230 的整块环形，面积是标签的十几倍。只给标签挂事件，用户戳扇区那一大块会毫无反应——这比不画扇区更糟，因为它看起来明明能点。视觉上能点的区域必须真的能点。

**实测**：`elementFromPoint` 在 r=210 外缘与 r=135 内缘都命中 `path.sector-shape`（父节点 `g.sector-g`），点击后正确进入第 2 步。`test-render.mjs` 加两条断言守这个：`每个扇形本体都绑了 click`、`点扇形本体进入第 2 步（场合）`（37 → 39 项）。

**代价**：同一个动作有两条触发路径（分组 + 按钮），逻辑必须共用，否则会出现「点标签和点扇区结果不一样」。实现上把三态处理收进 `setOn` 与 `pick`，两条路径只负责调用。

## D19 · 手机适配靠 `vh` 兜底，不只靠 `vw`

**决定**：`.disc` 宽度从 `min(88vw, var(--discw))` 改为 `min(88vw, 62vh, var(--discw))`，并新增矮屏档 `@media (max-height: 700px)`。

**理由**：只写 `vw` 时圆盘宽度只与屏幕宽度挂钩。iPhone SE（375×667）上圆盘 345px，加上头部与提问区共占 675.6px，**超出首屏 8.6px**——用户要滚一下才看得全圆盘。加 `vh` 约束后矮屏自动收缩，仍是正方形。

**实测五档**（ego-browser `Emulation.setDeviceMetricsOverride`）：

| 机型 | 修复前 | 修复后 |
|---|---|---|
| iPhone SE 375×667 | 首屏 ✗ 超 9px | 首屏 ✓ |
| 扇区触控尺寸 | 48×44 | 56×44 |
| iPhone 14/15 390×844 | 首屏 ✓ | 首屏 ✓ |
| Android 360×740 | 首屏 ✓ | 首屏 ✓ |
| Pro Max 430×932 | 首屏 ✓ | 首屏 ✓ |
| iPad 768×1024 | 首屏 ✓ | 首屏 ✓ |

五档全部通过：无横向滚动、标签截断 0/6、扇区 >= 56px。

**代价**：`vh` 在移动端地址栏收放时会跳动，所以只用于圆盘一个元素，且给了 `56vh` 与 `50vh` 两档而非紧贴 100vh，留出缓冲。
