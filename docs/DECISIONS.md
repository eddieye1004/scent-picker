# 决策记录

每条都是**已拍板**的，不是待选方案。左侧是当时的选项，右侧是结果与理由。

---

## D01 · 数据规模：400 瓶，不做全量

> **修订记录（2026-10-28）**：初版定为 200 瓶。后因圆盘第二层要按子家族展开，200 瓶撑不住——最薄的子家族只有 3 瓶，点进去等于空列表。`build-data.js` 加了 `--sub-quota` 子家族保底配额后扩到 400 瓶（32 个子家族最少 7 瓶）。

**选项**：抓全量（源站数千瓶）/ 抓 400 瓶

**决定**：400 瓶。

**理由**：全量抓取意味着要处理缺失字段、重复条目、异常香调列表的时间成本，而这个项目的核心风险不在数据量，在**推荐逻辑能不能讲清道理**。400 瓶足以覆盖 6 大家族 × 13 个源家族 × 32 个子家族，每个子家族至少 7 瓶。数据管线的 `build-data.js` 保留着，再扩只是改配额参数加一轮清洗。

**代价**：用户心里已经有的那瓶大概率不在库里。这点写进了 README 的"已知局限"。

## D02 · 应用层只用结构化事实字段；上游数据集原件随仓库分发（已修订）

> **修订记录（2026-10-28）**：本条初版写的是"原始数据不入公开仓库"，那是在**误以为 `perfumes.jsonl` 是我们自己抓的**前提下写的。核查后前提被推翻——它是上游主动以 CC BY 4.0 公开发布、供再分发的数据集文件本身（见 COMPLIANCE.md 第一节）。原文与仓库实际状态矛盾，故修订。修订依据：`git hash-object` 本机副本 = `8c745960a9bd7796bce68518e82f19ff17eaaaf1`，与上游 `perfumes.jsonl` 的 git blob sha 逐字节一致。

**选项**：把上游数据集原件一起入库 / 只提交清洗后的结构化字段

**决定**：两者都做，但**分工明确**——

| 位置 | 内容 | 用途 |
|---|---|---|
| `data/source/perfumes.upstream.jsonl` | 上游 CC BY 4.0 发布的原件（1.1 MB / 1,320 行，含 `description` 原文） | 可复现性：`build-data.js` 离线即可重建，且保留上游原貌便于比对 |
| `data/perfumes.json` | 清洗后的 400 瓶结构化事实（**不含 `description`**） | 应用层唯一数据源，前端只读这份 |

**理由**：许可允许再分发，不等于应用层需要搬运全部字段。

- 事实字段（香调名、品牌、家族）不受版权保护，直接用于应用层
- `description` 是 Scento 撰写的独创性文字。**应用层不呈现它**——不是因为不能（CC BY 4.0 允许），而是因为第一人称问卷的推荐理由必须能反推到用户自己的答案，第三方文案做不到
- 原件保留在 `data/source/` 且已署名，满足 CC BY 4.0 的 Attribution 与 Indicate Changes 两项义务（详见 COMPLIANCE.md）

**代价**：仓库多 1.1 MB。换来的是任何人 clone 后 `node scripts/build-data.js` 就能复现 `data/perfumes.json`，不需要联网、不需要信任我们的抓取过程。

## D03 · 大模型只润色不参与选品

**选项**：让模型直接看用户答案推荐 / 规则引擎选品 + 模型生成理由

**决定**：规则引擎选品。理由文案也用模板拼接，**运行时完全不调模型**。

**理由**三条：

1. **稳定性**：同一个问题问两次，模型可能给两瓶不同的香。推荐器不可复现是致命的。
2. **可验证性**：规则引擎的每一条理由都能反查到"你第 2 题选了约会 → 这瓶时段含 evening"。模型的理由是生成的，可能是幻觉（"这瓶有香草"而实际没有）。
3. **安全性**：纯静态站，前端调模型 API 意味着 API Key 必须暴露在浏览器里。

**代价**：理由文案是模板化的，句式重复度较高。缓解办法是每条理由绑定**具体的命中项**（"含你点名的佛手柑"而不是"符合你的喜好"），让重复的句子里填的是不同的证据。

## D04 · 家族体系：源站 13 类映射到面向用户的 6 类

**选项**：直接用源站家族名 / 自建一套 / 映射

**决定**：映射，`sourceFamilyMap` 手工表。

**理由**：源站的家族名（`Orchard Fruit`、`Velvet Sweet`、`Green Leaf`）对新手是黑话。但另起一套会让数据失去可追溯性。映射表让两边都保留：

```
用户看到的：美食调 / 木质调 / 花香调 / 柑橘调 / 清新调 / 琥珀调
数据保留的：Velvet Sweet / Woody / Floral / Citrus / Fresh / Amber & Resin
```

**代价**：映射有主观成分。`Orchard Fruit` 被归到花香调而非果香调，是因为源站这个家族下的代表香（Aventus）实际偏果香木质——这直接导致了 D08 的锚点层修复。

## D05 · 前端零构建：原生 ES Module

**选项**：React + Vite / 原生

**决定**：原生，无 `package.json`，无 `node_modules`。

**理由**：目标用户是"有基础开发能力的新手"。第一次 clone 下来如果先要 `npm install` 然后遇到 node 版本冲突，项目就死在这一步了。现在 `node server.js` 就能跑。

**代价**：没有组件化，`app.js` 单文件约 400 行。这个体量下可接受；再大就该引入构建了。

## D06 · 三个独立测试脚本，不用测试框架

**选项**：Vitest / Jest / 手写脚本

**决定**：手写，零依赖。

**理由**：与 D05 同理。而且这三个脚本的分工比框架更清楚——它们不是单元测试，是**三种不同粒度的体检**：

- `test-scoring.mjs`：穷举所有答案组合（105 项），验引擎不崩、结果幂等、讨厌项生效
- `test-render.mjs`：DOM 桩跑完整流程，验文案与三调渲染（47 项）
- `qa-data.mjs`：数据层体检，验结构、唯一性、家族覆盖、可溯源

**代价**：没有 watch 模式，每次改完手动跑三行命令。

## D07 · 视觉验证：从"完全不做"改为"用本机 Edge 无头"

**最初尝试**：puppeteer / playwright 截图对比

**结果**：本机沙箱拒绝。它们自带的 Chromium 启动时 mojo IPC 通道被策略拦截，进程起不来。

**替代方案（第一版）**：实现了一个最小 DOM 桩（`el` / `appendChild` / `textContent` / `dataset`），让 `app.js` 真的执行完整四步流程，再对其产出的文本断言。

**这条的边界必须说清**：它证明**逻辑与文案正确**，不证明**CSS 视觉表现**。布局错位、字体溢出、移动端塌陷这类问题它一个都抓不到。README 里因此留了一条"人工在真实浏览器看一遍"。

**后续更正（已实测）**：上面那句"本机无法截图"是**错的，只对 puppeteer/playwright 成立**。本机装了 Edge，直接用它的 `--headless=new --screenshot` 是可行的：

```
msedge.exe --headless=new --disable-gpu --no-sandbox ^
  --user-data-dir=<临时目录> --virtual-time-budget=7000 ^
  --window-size=1280,1000 --screenshot=shot.png ^
  http://127.0.0.1:8123/
```

配合 `--dump-dom` 还能拿到真实渲染后的 DOM（本文件里"结果页文本"的核查就是这么做的）。
**教训**：把"某个工具被沙箱拦了"记成"这件事做不到"是偷懒的归因。换一个已装在本机的浏览器就绕开了——先穷举本机已有的可执行文件，再下"做不到"的结论。

**残留局限**：静态截图看不出交互态（hover/focus）、也说不了移动端真机上的滚动与手势表现。

## D08 · 加"情绪锚点香调"层（本版最重要的一次修复）

**问题**：初版只按家族向量打分。实测"清冷 + 约会 + 强度 2"时，**Creed Aventus 排第一**（80.6 分）。

为什么错：Aventus 被源站标成以 floral 为主的 `Orchard Fruit`，家族向量与"清冷"不冲突。但"清冷"在气味语义上要的是鸢尾、紫罗兰、柏树那种**冷感**，而 Aventus 是明亮的果香木质。家族层太粗，区分不出来。

**修复**：在家族层之上加一层**情绪锚点**——每种情绪对应 5 个锚点香调：

| 情绪 | 锚点香调 |
|---|---|
| 清冷 | 鸢尾、紫罗兰、柏树、香根草、焚香 |
| 温暖 | 香草、琥珀、零陵香豆、肉桂、檀香 |
| 干净 | 皂感、白麝香、棉花、醛、铃兰 |
| 神秘 | 乳香、没药、皮革、广藿香、藏红花 |
| 明亮 | 佛手柑、柠檬、橙花、葡萄柚、黑加仑 |
| 慵懒 | 麝香、椰子、无花果、零陵香豆、檀香 |

权重 22 分（仅次于家族 52 分）。修复后同一查询的第一位变成 **Byredo Gypsy Water**（含鸢尾 + 焚香），语义才对齐。

**教训**：**粗粒度分类永远会漏掉语义。** 当用户用感受性词汇（"清冷"）提问时，必须有一层能直接落在具体材料上的映射，否则分类体系再整齐也是错的。

## D09 · 源家族 + 品牌双重去重（前三名互不重复）

**问题**：初版前三名可能全是 `Velvet Sweet`，对用户毫无参考价值——三瓶闻起来是同一个方向。

**第一版修复**：排名阶段做贪心去重，已出场的源家族在后续候选中降权。

**第二次修复（2026-10-28 实测发现第一版不够）**：只用家族去重仍会被单一品牌垄断。样本里 Byredo 有 9 瓶、横跨 4 个源家族，家族层去重拦不住——它们的源家族确实不同。

实测（复现旧逻辑，遍历 6 情绪 × 5 场合 × 6 个点名香调 = 180 组）：
- 不带点名香调：30 组里 **2 组**品牌重复（`cold/date` 出 Byredo + Zoologist + Byredo）。
- 带点名香调：180 组里 **18 组**品牌重复，最差的一组 `cold/date/Bergamot` 是 **Byredo + Byredo + Byredo** —— 三瓶同一个牌子。

走「点一个喜欢的香调」这条路时必然触发，不是极端案例。

**修复**：品牌与家族**同时**去重，分三轮放宽：
1. 首轮要求家族不同 **且** 品牌不同；
2. 不够数则放宽到"品牌不同"（允许同家族）；
3. 再不够则彻底放宽，保证一定凑满 topN。

**验证**：`scripts/test-scoring.mjs` 的 T11 遍历 30 组无香调组合，断言三瓶品牌互异；修复后 30/30 通过，测试总数 105 → 106。

**理由**：推荐 3 瓶的目的不是"把最像的都给你"，是**给你三个可以对比着试的方向**。同品牌三连会直接摧毁这个目的——而不只是"看起来不够多样"。

**数据事实**：400 瓶里 52 瓶源站没标浓度（占 13%）。

**选项**：按品牌/家族猜一个 / 留空

**决定**：留空，界面显示"持香未标注"。

**代价**：24 瓶的卡片看起来"信息不全"。这是诚实的代价。

## D11 · 部署目标：GitHub Pages（纯静态）

**决定**：纯静态，无后端。

**理由**：推荐逻辑全在客户端（D03），没有需要保护的服务端逻辑，也没有用户数据要存。静态托管意味着**零成本、零运维、不会挂**。

**代价**：数据更新需要重新构建并提交。400 瓶的量级下，这反而是优点——每次数据变更都有 git 记录。

## D12 · 香调匹配改为「按词匹配 + 显式别名」

**决定**：不用双向子串（`pn.includes(n) || n.includes(pn)`），改为把香调名切成词，按词边界匹配，并以 `taxonomy.noteIndex.entries[].aliases` 显式补充同义写法。匹配逻辑集中在 `src/notes.js`。

**理由**：子串匹配会造成用户能感知到的错判。实测数据（当时库容 200 瓶）：
- `晚香玉 tuberose` 声称命中 **72 瓶**，实际只有 **9 瓶** —— 因为 `Tuberose` 里含 `rose`，把玫瑰全吃进来了。
- `玫瑰 rose` 声称命中 **85 瓶**，实际 **65 瓶** —— 误吃 `Tuberose` / `Rosemary` / `Rosewood` / `Pomarose` / `Rosehip`。
- 连带 `铃兰 lily of the valley`（原被 `lily` 子串拉进 5 瓶）、`檀木 sandalwood`（原靠 `sandalwood.includes('wood')` 凑）同样受影响。

**代价**：需要维护 `aliases` 表。当前只补了 6 条（雪松/海水/绿茶/无花果叶/橙花/苦橙叶），其余靠按词匹配已能覆盖。新数据和失败样本出现时要继续补。

## D13 · 死选项按命中数过滤，不上屏

**决定**：第 4 步的香调 chip 只渲染「在当前样本里至少命中 1 瓶」的条目（`src/notes.js` 的 `usableEntries()`），计数由数据算出，不写死。

**理由**：`可可 cocoa` 在当时的 200 瓶里出现 **0 次**。用户勾了它，界面给了勾选反馈，但打分环节没有任何一瓶能命中——等于骗了一次点击，且用户无从知道为什么没效果。

**代价**：`usableEntries()` 每次要扫 200×40。已在 `app.js` 里按数据对象引用缓存结果，重渲染不重算。数据换掉时缓存自动失效。

**实测**：40 → 39，隐藏 1 个（可可）。首屏 16 个仍覆盖全部 6 个家族。

**未做**：没有反过来「扩充香调到数据里」（比如把 cocoa 加到某些美食调香水），因为那是改数据，超出修 UI 的范围。

## D14 · 前两步改成 HUD 圆盘，但命中区仍是真实 button

**决定**：第 1 步（情绪，6 项）与第 2 步（场合，5 项）从纵向列表改成环形圆盘选择器。**扇形用 SVG 画，但可点区域是绝对定位的真实 `<button>`**。

**理由**：用户明确要「钢铁侠操控台那种圆盘」。但纯 SVG 交互有三个硬伤：480×480 坐标系里做命中测试拿不到 44px 触控保护；键盘 Tab 进不去；`role="radio"` 语义没法挂在 `<path>` 上。所以形状归 SVG，语义归 HTML。

**做法**：
- `annulusPath(rOut, rIn, a0, a1)` 拼环形扇区路径，`gapDeg: 1.6` 留出缝
- 第一个扇区正对 12 点（`startBase = -90 - half`），读起来像仪表盘
- 标签落 `midR = (rIn + rOut) / 2` 极坐标点，转百分比定位，保证不出圆
- 盘心 `.disc-hub` 34% 直径，hover/focus 时显示该项说明；离开后回退到已选项
- roving tabindex：选中项或首项 `0`，其余 `-1`；方向键移动焦点时同步搬 `tabindex`，否则 Tab 离开再回来会跳回第 0 项（实测过这个 bug）

**代价**：`scripts/test-render.mjs` 的极简 DOM 桩要补三样能力才测得动——`createElementNS`、`setAttribute('class')` 同步 `classList`、`tag.class` / `[attr="v"]` / `.a.b` 选择器。补之前 4 条断言全假失败。

**实测**（真实浏览器）：圆盘 560×560、盘心 190.4×190.4（=34%）、扇区最小 56×59.2（>=44）、6 个标签零溢出零重叠、无横向滚动条。

## D15 · 控件边界单独用 `--edge`，不再复用 `--line`

**决定**：`:root` 新增 `--edge: #42688f`（对 `--bg` 3.39 : 1），`.sector-shape` 的 `stroke` 从 `--line` 换成 `--edge`。`--line` 降级为「纯装饰分隔线」。

**理由**：WCAG 1.4.11 要求 UI 组件边界 >= 3 : 1。实测 `--line #21324a` 只有 **1.52 : 1**，拿它画扇形描边等于没画——用户看不出哪里能点。而纯填充色无论怎么提亮都到不了 3（`#1e3752` 也只有 1.62），深色主题下填充必然贴近底色，只能靠描边。

**代价**：多一个颜色变量。`scripts/test-contrast.mjs` 加了一组非文字对比度检查（PASS 20 → 25），并加了一条反向自检：`--line` 必须真的低于 3，否则说明「装饰色当边框用」这个错它抓不到。

## D16 · 库容从 200 扩到 400，且抽样按「家族 + 子家族」双配额

**决定**：`scripts/build-data.js` 加 `--limit 400 --sub-quota 6` 两个参数。家族保底之后再做一轮子家族保底，每个子家族至少 6 瓶。

**理由**：200 瓶时只按家族配额抽样，导致 5 个子家族几乎没有货——实测 `gourmand/boozy` 3 瓶、`gourmand/coffee-cocoa` 4 瓶、`fresh/green` 4 瓶、`fresh/tea` 6 瓶。这些子家族在第二层轮盘里是可选项，点进去只有 3 瓶，等于假选项。而全量 1,228 行里最少的子家族也有 24 行，说明不是数据不够，是抽样不均衡。

**实测**：模拟不同库容与保底值，`LIMIT=300 + SUB_QUOTA=6` 就已消除全部薄扇区；取 400 是因为用户要求「多加 200 瓶」。重建后 32 个子家族最薄 7 瓶（`coffee-cocoa`），其余 24 个都在 10 瓶以上。

**代价**：`perfumes.json` 从 261 KB 涨到约 500 KB。仍是单个静态文件，前端一次 fetch 即可，不值得为此上分页或数据库。

## D17 · 香调索引从 40 条补到 56 条，补的是空子家族而不是「热门的」

**决定**：新增 16 个香材，让 32 个子家族**全部**有香材挂靠。顺序是先补 0 香材的空子家族（`floral/soliflore`、`woody/woody-aromatic`、`gourmand/fruity-gourmand`），再补货量最薄的。

**理由**：点进一个子家族却看不到任何香材，和之前修掉的「死 chip」是同一类错误——界面说了有，实际是空的。补什么不能凭印象：先在上游 1,228 行里跑真实 surface 词频，只收命中数够的。

**实测剔除名单**（写在这里是为了下次不要重复试）：`narcissus` `banana` `black tea` `white tea` `earl grey` `mate` `chai` `whiskey` `brandy` `wine` `bourbon` `sake` `martini` `gin` `nettle` `moss` `bay leaf` `eucalyptus` —— 这些在数据里 **0 命中**，绝不能写进 taxonomy。

## D18 · 扇形本体自己绑定点击，不只依赖扇区上的标签按钮

**决定**：每个 `<g class="sector-g">` 直接挂 `click` / `mouseenter` / `mouseleave`，行为与标签按钮完全一致（同一份 `pick.current` 状态、同一套 `setOn`、同一个 `onPick`）。

**理由**：扇区是半径 104–230 的整块环形，面积是标签的十几倍。只给标签挂事件，用户戳扇区那一大块会毫无反应——这比不画扇区更糟，因为它看起来明明能点。视觉上能点的区域必须真的能点。

**实测**：`elementFromPoint` 在 r=210 外缘与 r=135 内缘都命中 `path.sector-shape`（父节点 `g.sector-g`），点击后正确进入第 2 步。`test-render.mjs` 加两条断言守这个：`每个扇形本体都绑了 click`、`点扇形本体进入第 2 步（场合）`（37 → 39 项）。

**代价**：同一个动作有两条触发路径（分组 + 按钮），逻辑必须共用，否则会出现「点标签和点扇区结果不一样」。实现上把三态处理收进 `setOn` 与 `pick`，两条路径只负责调用。

## D21 · 圆盘内圈加 36 道分度刻线，是功能暗示不是花纹

## D22 · 视觉最终定为瑞士国际主义，靠字号与留白，不靠质感

**决定**：`styles.css` 全量重写为 Swiss 风格——白底 `#ffffff`、墨黑 `#0e0e0e`、单一朱红 `#b3261e`、`--radius: 0`、无阴影、无渐变、无纸纹。层级只用字号（12/14/16/20/26/34/44）、字重（400/600/700）、留白和一根 8px 墨线。选中态的唯一手段是「填黑 + 文字反白」。

## D25 · 字阶收 7 档、字重分 3 层、动效收 3 档

**背景**：视觉定稿后回头看，CSS 里字号有 15 个档位（11.5/12/12.5/13/14/15/16/17/18/19/21/22/23/24/26/28/30/34/44），相邻档差 1–2px。人眼分辨不出这种差别，它只让样式表变长、让每次改字号都要重新判断"这里该用 23 还是 24"。

**决定**
- 字号：**12 / 14 / 16 / 22 / 26 / 34 / 44**。12 是 `test-contrast` 强制下限，44 只在 h1。
- 字重：**12px→500、16px→600、22–44px→700**。原先把 12px 小标签设成 600，比 26px 标题还响，层级是反的。
- 动效：**160ms**（普通颜色/位移，19 处）、**180ms**（盘心，8 处）、**120ms**（只给 `.fade-in`）、**900ms**（`busy-dots`）。原先 140/150/160 三个值差 10–20ms，纯属噪音。
- 强调色：朱红从 18 处降到 15 处。题号、结果页眉、选项箭头三处降成 `--ink-3`——它们只是装饰，红色只留在表达状态的位置。

**顺带修掉的三个真实缺陷**（都是截图/实测才发现的，测试当时是绿的）
1. **首屏自动聚焦第一个扇区**：新访客一进来「清冷」就戴红色焦点环、盘心写「正在看 清冷」，误以为已选中；真正的空态永远不出现。删掉自动聚焦，键盘仍可 Tab 进入。
2. **悬停反馈实测只有 1.03:1**：`fill: var(--bg-2)` 是 #f5f5f5，对白底几乎不可见。深色主题下"换浅一档"够用，搬到浅底就失效——这类问题换肤时最容易漏。改成描边加粗到 2px + 填充 `--bg-3`。
3. **悬停文字标签时扇形不亮**：按钮盖在扇形上方，只给 `<g>` 挂 `mouseenter` 会断在用户最常指的位置。

**代价**：`--accent` 少三处装饰用法后，红色在页面上的"存在感"更依赖进度条和盘心；这是有意的——颜色越少，用它的地方才越像信号。

## D26 · 喜欢/讨厌两栏必须互斥

**背景**：实测发现同一个香调可以同时在「我喜欢这些味道」和「我受不了这些味道」两栏勾上（脚本一次点了琥珀/香草各两次，四枚 chip 全亮）。

**这不只是显示问题**：进引擎后喜欢分与讨厌分互相抵消，结果卡片的理由里**完全不提用户点名的香材**。用户看到的是「我明明选了它，为什么理由里没有」——比不推荐更糟，因为它让整个推荐失去可信度。

**决定**：勾一边时直接从对面数组里摘掉同一个 `en`，并把对面那枚 chip 的 `aria-pressed` / `neg` 同步关掉。两栏各建一个 `en → chip` 登记表，**不靠 DOM 顺序猜是哪一栏**（加了隐藏折叠区之后，"第一个 `.chips` 是喜欢栏"就不成立了）。

chip 加 `data-col="liked|disliked"`，让测试也能按列定位。`test-render` 的第一版断言拿 `chips.length` 当分界，而 `chips` 是静态快照，`slice(自身长度)` 永远是空数组，假失败成「未找到副本」——这个坑值得记。

**实测**：点喜欢·琥珀 → 喜欢[琥珀]；点讨厌·琥珀 → 喜欢[] 讨厌[琥珀]；再点喜欢·琥珀 → 喜欢[琥珀] 讨厌[]。

## D27 · 主色定克莱因蓝 #002FA7，蓝只留两处高分量

**背景**：D 稿的主蓝是 `#0a5cff`（HSL 220/100/52），白底 4.19:1。做 76–132px 大字时刺眼，且被用在四处（`.kick` / `h1 em` / 进度首段 / 盘心主词），从 13px 到 132px 全尺度上都是同一块纯色。用户给的原话是「塑料感、很 AI」。

**诊断出五条具体原因**：① 明度 L=52 太高，大字像屏幕自己发光；② 饱和度全程 100 无衰减——现实里不存在 S 恒 100 的大色块，这是塑料感在数学上的根源；③ 蓝色面积过大，13px 到 132px 都在用；④ 全站 `box-shadow: none`，没有任何光照模型，`h1 em` 是纯填充；⑤ 边缘只有抗锯齿硬边，无噪点、无渐变、无边缘受光。补一条更根本的：色相 220° 是数码蓝，跟香水原料（树脂/花瓣/苔藓/酒精）没有关系——这是「大众感」的真正来源。

**决定**：换成克莱因蓝 `#002FA7`（HSL 223/100/**33**，白底 **10.69**），它接近伊夫·克莱因 1960 年注册的 IKB，明度只有 33%，重量感接近墨，能和 `--ink #0e0e0e` 并置而不被压住。四档色值：

| 档位 | 色值 | HSL | 白底 | 用途 |
|---|---|---|---|---|
| 主色 | `#002FA7` | 223/100/33 | 10.69 | `h1 em`、主按钮、选中描边 |
| 暗部 | `#001A5E` | 223/100/18 | 16.04 | 渐变尾、已完成进度段、阴影色相 |
| 高光 | `#3D5FC4` | 225/**53**/50 | 5.78 | 渐变起点、进度末端 |
| 环境反光 | `#8A93B8` | 228/**24**/63 | 3.02 | 仅 1px 描边，**禁止承载文字** |

高光档把饱和度从 100 降到 53，这一刀就是去塑料感的关键——材质的高光永远比固有色更淡、更灰。

**蓝只留两处**：`h1 em`（渐变裁进文字）与主按钮渐变。其余五处原朱红全降 `--ink`。改动后蓝像素从 91,533 降到 36,059（**−61%**）。

**去塑料感其余五手段**：feTurbulence 噪点 `opacity:.032; mix-blend-mode:multiply`；阴影用同色相 `rgba(0,26,94,*)` 而不用黑（黑会把暖白底压脏）；按钮 `inset 0 1px 0 rgba(255,255,255,.14)` 做边缘受光；选中扇区用 `rgba(0,47,167,.07)` 水洗而非实色；盘心径向双层渐变。光影方向统一左上受光、右下投影。

## D33 · 盘心的可见边界按圆弧算，不按矩形算

| 390×844 | 展开 | `.hub-go` | 168 | 162 | 5.7px |
| 360×740 | 展开 | `.hub-go` | 156 | 140 | 15.8px |

## D34 · 子类方格的手臂是零宽轴，不是满尺寸盒子

**问题**：展开态（选了大类、未选小类）后整页可以左右晃。实测 `documentElement.scrollWidth 401 / clientWidth 360`（390 视口 435/390、320 视口 356/320）。方格本身没出屏（`bad: []`），`.disc.wheel` 也没出屏（312 宽、左 24 右 336）。

**根因**：`.sub-arm` 是 `position:absolute; inset:0` 的满尺寸盒子，靠 `transform: rotate(θ)` 把方格送到圆周上。盒子绕中心转 θ 之后，它的**角**必然扫到圆盘外面——360 视口实测 `l:-39 r:399 w:438`，六个手臂里最宽的那个把文档撑到 401。溢出的是空手臂，肉眼看不见，所以截图看不出问题。

**改法**：手臂不需要面积，只需要一条过圆心的轴。
```css
.wheel .sub-arm {
  inset: auto;
  left: 50%;
  top: 0;
  bottom: 0;
  width: 0;
  transform-origin: 50% 50%;
}
```
旋转一条零宽线不产生任何横向延伸。方格本来就挂在手臂顶端，位置一个像素都没变（实测 `cells360` 前后 `outBy` / `clearHub` 完全一致）。

**验证**：三视口 `overflowX` 全部 `false`、`scrollW == clientW`（360→360、390→390、320→320）；`scripts/test-render.mjs` 加一条断言钉住 `width: 0` + `inset: auto`，共 69 项。

**这条为什么值得记**：绝对定位 + `inset:0` + 旋转，是「容器自己不可见却撑开文档」的典型；用截图和元素自身 boundingRect 都查不出来，只有扫 `body *` 的 `right > clientWidth` 才抓得到。

## D35 · 反馈态补齐：写之前先证明这条选择器能生效

**问题**：交互审查时列出「按下无反馈」的候选有四个 —— `.disc-hub`、`.sub-sq`、`.hub-reset`、香调两栏的标签。其中只有两个是真的。

```css
}
```
`:focus-visible` 也走同一条底色：Tab 到方格时只有一个孤零零的焦点环，没有"这块被我选中了"的归属感。

## D37 · 六点交互改造：图案按小类各画一枚，选中不翻整盘

**背景**：用户给了六条要求（引导是否可不选内圈 / 四格与圆盘视觉呼应 / 悬停实时预览 / 每小类专属标识 / 确认后别整盘变黑 / 内圈按区分度分档）。其中两条直接推翻了旧结论，必须记账。

### ④ 推翻 D32 的「图案只编码家族」

D32 的结论是「一枚图案编码家族，同族小类共用一张」。当时的依据是实测 `platefam.mjs`：38 个小类里 **32/32 的代表香材全落在同一个 family**，逐味画会出来一排一样的图标。

用户第 4 点明确要求「古龙水型用古龙独有标识，青绿柑橘与芳香柑橘各自不同」。**这是需求变了，不是原判据错了**——原判据证明的是「按家族画不会重复」，不能反推「按小类画必然重复」。真正需要换的不是粒度，是**画什么**：不画「这味香材属于哪个家族」的结构示意，画**这味香材本体**。

32 枚全部重画（`SUB_MARKS`，key 为 sub id，24×24、无填充、返回 `[{tag,attrs}]`）：柠檬=横置尖椭圆、佛手柑=带颈梨形、橙花=五瓣、葡萄柚=正圆厚皮分瓣、香根草=扇形根须、皮革=圆角皮片+8 缝线孔、酒香=酒杯轮廓。`scentPlate` 选形改为先查 `SUB_MARKS[sub.id]`，查不到才退回家族母题（**宁可退回家族图，也不画一个假的专属图**）。

24px 下三条硬限制（写进块首注释）：
1. 两个相邻的小圆点会被读成一张脸 —— 不留并排小圆
2. 不与主形同心的线段会被读成螺旋 —— 内部线必须对称或贯穿
3. 外轮廓差异 >> 内部细节差异 —— 优先换轮廓，内部线不超过两条

`check-submarks.cjs` 核对：taxonomy 32 subs = SUB_MARKS 32 keys，缺 0 多 0。

### ⑤ 推翻「选中 = 整盘翻墨」

旧实现：`is-picked` 时 `.disc-core` 背景换 `var(--ink)`、文字反白、线稿换白线。用户原话「避免内圈直接变黑，反差过大不优雅，参考苹果、Oura」。

改成三层同时表达，**没有一层靠整块翻色**：

2. **被选中的那一格自己填实 `--blue` + 白字**（面积小、对比 10.69:1、位置明确）
3. 盘心文字回墨色系，标本线稿从白线换深线

### ⑥ 内圈按区分度分档

## D38 · 同族标识不许撞形：判据是「用户并排看是不是同一枚」

**背景**：D37 给 32 个小类各画了一枚标识。用户第 4 点的原话是「每个小香型使用具辨识度的专属标识」——「有专属标识」不等于「有辨识度」。本轮把 32 枚摊成对照图（96px 与 44px 两档）逐族看，抓出两处真实撞形，它们都通过了「图元数不同」「几何签名不同」这类断言。

### 抓缺陷的方法

三个脚本，缺一不可，各有各的盲区：

| 脚本 | 做法 | 能抓住 | 抓不住 |
|---|---|---|---|
| `markpairs.mjs` | 按族排成对照图，96px + 44px 两档并排 | 人眼一看就一样的 | 需要一格格数 |
| `markaudit.mjs` | 光栅化到 48×48，两两算 IoU + 召回率 | 大面积的形似 | 细笔画（1.2px）的 IoU 天然低 |
| `test-render` 几何签名 | 比对 `tag` + 全部属性 | 完全重复 | 只差 1–2px 偏移的 |

**IoU 会骗人**：`mossy vs woody-aromatic` 只有 0.447，看着「差得还够」，但截图里两枚在 44px 下是同一张图（细高枝 + 顶端一个圆点，只差 1px 横向偏移）。反过来 `white-floral vs vetiver` 的 IoU 0.612 却没人会认错（一个细长花瓣、一个扇形根须）。**原因是 IoU 对描边宽度极度敏感**：两个 1.2px 描边的图，只要轮廓错开 1px，重叠面积就腰斩。所以 IoU 只能用来排序找嫌疑，判决必须看图。

跨族撞形不用管：外圈一次只展开一族，用户永远看不到两族并排。真正要守的是**同族内部**（`audit.json` 按 `families[].subfamilies` 分组过滤）。

### 两处缺陷与两次返工

**① `mossy`（苔藓木质）vs `woody-aromatic`（芳香木质）** —— 原都是「主枝 + 两对短枝 + 顶端一点」。
- 返工 1：改成「宽拱 + 三根等距竖线」。不撞形了，但读成拱桥/提篮，不像苔。
- 返工 2（定稿）：「一条树皮横线 + 上面一丛长短不齐的短毛」。苔藓没有主干、也不成枝，它是贴在树皮上的一层绒毛。横线是树皮，短毛是苔。这是木质族里唯一的横向构图，六枚的外形分别是 横/枝/扇形/方/年轮/块。

**② `vanilla-gourmand`（香草甜）vs `coffee-cocoa`（咖啡可可）** —— 原都是「斜置竖椭圆 + 一道缝」，只差旋转 8°。
- 返工 1：香草改弯月牙。不撞形了，但读成树叶/香蕉，缺「荚」的身份。
- 返工 2：加荚柄。还是读成带柄的叶子。
- 返工 3：压窄成 1:6 长宽比。仍像叶子——**带中缝的尖椭圆本来就是我们画叶子的方式**（这一族旁边就有 `green` 是叶子）。症结不在胖瘦。
- 返工 4（定稿）：换线索。荚的特征是「籽沿轴向排」，叶脉是「向两侧分叉」。加三道横跨的短线（种子），叶脉永远不长这样。同时把咖啡可可从「竖椭圆」改成**正圆 + S 缝**——可可豆横切本就是扁圆。同族五枚轮廓现在是 弯荚/正圆/竖尖/心/杯，没有两个相似。

### 定稿判据（写进 `test-render.mjs`，4 条）

1. **每个小类都有标识**（`typeof MARKS[id] === 'function'`）—— 缺一个会静默退回家族母题，用户看到的图和他选的格不对应，而所有既有断言都发现不了。
2. **没有多余标识**（不画数据里不存在的格）。
3. **32 枚图形全不相同** + **同族内部不重复** —— 用几何签名（`JSON.stringify(SUB_MARKS[id]())`）比对。测试环境没有 canvas，不做光栅化；几何签名能抓住「整枚完全一样」，抓不住像素级形似，后者靠 `markpairs.mjs` 人眼过。
4. **每枚不是孤点孤线** —— 判据是「图元数 + 曲线段数 ≥ 2」。**多次修正过这条**：先写「图元数 ≥ 2」，把 `vetiver`（一束五根曲线打包在一条 `path` 里）、`spicy-amber`（一根连续卷进的肉桂卷）判成失败；再写「`M` 命令数 ≥ 2」，`spicy-amber` 仍失败——它就该是一笔到底。最终用 `[CLQ]` 段数兜底。

### 断言与脚本的边界

- `markaudit.mjs` 的光栅化**必须**先注入 `const r2 = ...`：`SUB_MARKS` 依赖 `app.js` 里的 `r2()`，只切 `SUB_MARKS` 块会报 `r2 is not defined`、整页白屏（`marksheet.mjs` 踩过一次）。
- `SUB_MARKS` 块要用**大括号配对**切，不能用正则找 `^};` —— 块内的函数体自己有 `}`。
- 这两条脚本不进仓库、不进 CI，改图案时要手动跑。理由：它们依赖本机 Edge 的 headless 通道，同一份代码在 CI 上跑不通（会误报「全部通过」）。
- **改图案必须重跑四视口**：盘心是圆，图为 44–88px，高度一变就可能把「换一个大类」顶出弧外。实测改完 `overflow []`、`hubScroll sh==ch` 四视口全过。

## D39 · 五条交互改造：三格弧窗、返回入口移出盘心、文案去句号

**背景**：用户 m10062 提了五条（去句号 / 返回入口 / 小圈可点切大类 / 中圈改弧上旋转 / 图标质感统一）。五条里没有一条是"样式微调"，全部改到了结构。这里记取值理由与两次被截图否掉的实现。

### 一、去句号：只剥末尾，不动句中

`strip-period.cjs` 只匹配 `/[。]$/` —— taxonomy 70 处、`app.js` 9 处，`scoring.js` 0 处。**句中句号必须留**：`STEPS[0].help` 是「不用记名字。外圈挑大方向，中圈再收窄一层；不确定就只选外圈」，第一个句号断开的是两件事（做什么 / 怎么做），删掉它两句话会黏成一长句。

两条守门断言（`test-render.mjs`）：扫 `families[].{oneLine,style,wear,avoid,desc}` 与 `subfamilies[].{desc,descWheel}`；以及把 `appRoot.textContent` 按行切后判 `/。$/`。**页脚的「已修改。」是独立文本节点，不是文案句末**，断言按行切正好把它排除（它不是行尾）。

### 二、返回入口：从盘心搬到盘外，因为它和主操作抢位置

原来「换一个大类」是盘心底部一个 `<button class="hub-reset">`。问题有两层：

1. **位置冲突**：盘心同时要放 kicker / 主词 / 说明 / 标本 / 「就选「X」，下一步」/「中圈可不选」，再加一个「换大类」是第七件东西。实测盘心圆 270px（桌面）/ 156px（360），塞第七件就把某一件顶出弧外。
2. **语义冲突**：「换大类」和「就选「X」，下一步」是**相反方向的两个动作**，一上一下并排在盘心中央，拇指在 44px 触屏上够错一个就反了。

定稿：`.wheel-back` 绝对定位在控件左上角（`left:0; top:0`，窄屏 `-2px / -6px`），胶囊形 `border-radius:999px`、`min-height:44px`、`padding:0 12px`、12px/500、`color:var(--ink-2)`。三态齐全：`:hover` 转 `--bg-2` + `--edge`；`:active` `translateY(1px)` + `--ink` 描边 + `--bg-3`（下沉 1px 是"按下去了"的最小可见信号，不需要缩放）；`:focus-visible` 2px `--blue`。

**[hidden] 的优先级陷阱**（这次又踩了一次）：`.wheel-back[hidden] { display: none; }` 必须显式写。UA 样式表里 `[hidden]` 只有 `display:none`，作者样式里任何 `display:inline-block` 都能顶掉它 —— 上一轮 `.hub-skip` 就是这么在闭合态露出来的。

### 三、小圈可点切大类：先解决一堵"看不见的墙"

`.sub-ring` 在 `is-open` 时是 `inset:0`（铺满整个控件矩形）+ `pointer-events:auto`。它视觉上只有外面的三格和两枚圆钮，但**命中判定基于几何盒子不是像素**——铺满的透明 div 会把下面 6 个扇区的点击全部吃掉。所以"让缩小后的盘可点"的第一步不是加事件，是把这堵墙拆了：

```css
.wheel.is-open .sub-ring { pointer-events: none; }
.wheel .sub-arm { pointer-events: none; }
.sub-arm .sub-sq, .sub-arm .spin-nav { pointer-events: auto; }
.wheel.is-open .sector-g { opacity: .30; pointer-events: auto; cursor: pointer; }
```

`.sub-arm` 也是同理：`_wheel4c.css` 里已改成零宽轴，但仍要显式 `pointer-events:none`，否则轴上那条 0 宽的线在部分引擎里仍参与命中。

**可点性要看得见**：`.30` 是"还在，但不是当前的"；悬停到非当前扇区抬到 `.55`（`.is-hot:not(.is-on)`）；当前那个保持 `1`。盘心 kick 从「已选定大类」变成「点一下换到」+ 新大类的名字与描述 —— 用户还没松手就知道点下去会发生什么。这条靠 `const showFamId = hoverFam || selFamily;`（悬停优先于已选）与 `hoverOther = !!(hoverFam && hoverFam !== selFamily)` 分支实现。

### 四、中圈改弧上旋转：为什么是三格，为什么不用 transitionend

原来一次把 tier1 铺成一整圈方格，末尾一枚 `+N` 虚线格点开铺全。两个问题：一圈 5–7 格在新手眼里是"又一份问卷"；`+N` 是个抽象符号，点之前不知道后面有几个。

定稿：**三格弧窗**（左/中/右，`SPIN_DELTA = 44`，即两侧格偏离正上方 44°），左右各一枚 44×44 圆钮 `‹` `›`（`SPIN_ARROW = 90`，正 9 点 / 3 点钟方向，压在那条 1px 虚线上）。**转动即选中**（`turnBy` 里 `renderSpin` 后立刻 `chooseSub`）—— 不做"先转到位再点确认"的两段式，因为弧窗只有三格，中间那格就是指针，再要一次确认等于让用户点两次同一件事。

- **中格 `.is-center`**：白底 + `--edge` 描边 + 阴影，字重 600；选中时自己填 `--blue` 反白。
- **侧格 `.is-side`**：`opacity:.34; scale(.84); font-weight:500`，悬停/聚焦抬到 `.72`。它们可点（点侧格 = 转到那一格），所以不能 `pointer-events:none` —— 只是"次要"，不是"不可用"。
- 入场动画 `@keyframes spinInNext/spinInPrev`：`translateX(±26px)` + opacity .2→1、200ms。方向要和用户点的那一侧一致，否则转起来像在打滑。

**不用 `transitionend` 状态机**：`test-render.mjs` 的 TNode 桩只调监听器、不派发 `transitionend`，写成状态机会让整条断言链在测试环境里永远停在中间态。改用「重建节点 + 一次性 CSS 动画」——动画只负责好看，状态由 `spinIdx` 这个整数决定，测试可复现。

**`armDeg = deg + 90` 是从旧代码抄来的错误换算**：旧的 `renderSpin` 拿到的 `midDeg` 是「0 = 正右」的极角，要 `+90` 换 CSS 旋转角；新参数 `deg` 本来就是「相对正上方」。不修的话中间那格会跑到 3 点钟方向。

**`tier` 降级为排序依据**：第⑥点本来用 tier 做"默认只铺差异大的"，现在一次只显示三格，`+N` 的动机（一次别给一堆）已经被弧窗解决了。tier 保留在数据里用于决定 `spinIdx = 0` 时停在哪，不再驱动渲染 —— `is-tier2` 类名与 `@keyframes sqIn` 一并删掉（`_wheel5.css` 6121 → 5307 字节）。**留着是两条永远为真的假守门**：`test-render.mjs:245/246` 当时正在读这两段 CSS 文本，而它们守的 UI 已经不存在。

### 五、图标质感统一：按包围盒归一，线宽按 1/k 补偿

32 枚标识的原始包围盒 `k` 从 **0.886（fougere，5.5×19.75）到 1.429（spicy-amber，11.25×12.25）**，最大最小差 **1.61 倍**。不归一的话同一屏里有的图明显大一号、有的小一号，"质感"碎在这里。

`markfit.mjs` 把每枚光栅化到 192×192 数着墨像素求 bbox，目标 `TARGET = 17.5`（viewBox 24 留 3.25 边距），`k = 17.5/max(w,h)`、`tx = 12 − k·cx`、`ty = 12 − k·cy`，结果写进 `SUB_FIT`（`app.js`）。

**线宽必须按 `1/k` 补偿**：

```js
a.push(['stroke-width', r2(PLATE_SW / fit[0])]);
```

不补偿的话 k=1.429 那枚被放大后线粗 2.6px、k=0.886 只有 1.6px，**同一份样式表读出两套粗细** —— 这是"每张图单独调了"的观感来源。实测：预览态玫瑰（k=1.2385）算出 0.57、选中态白花（k=1.0069）算出 0.7。

**预览态也要画图**（原设计是只有确认后才画）：不画的话用户转一圈看不到这味香型长什么样，第 4 点"辨识度"就只在最后一步兑现。常态 `.plate-svg{stroke:var(--ink-3); transform:scale(.92)}`、选中 `{stroke:var(--blue); transform:scale(1)}`，`.plate-cap` 的 opacity 从 .6 到 1。

### 六、截图才查得出的缺陷：kicker 被一行老规则藏掉了

## D40 · 两层切换的进出场：大圈退到幽灵态、中圈反序收、返回分两级

**背景**：用户提了三条（圆盘层级状态机 / 中圈 7 段谱 UI 不动 / 动效与视觉升级），
随后补了第四点：「当用户点击进入第二圈时，第二圈以动效呈现的同时，第一圈（大圈）
配合播放相应的消失动效；当用户通过按钮返回初始的大类状态时，第二圈和大圈都需
分别播放对应的消失与出现动效，确保两个圈层切换过程衔接自然、节奏一致。」

### 一、先把「返回」的两个层级分清（这是本轮唯一的口径改动）

上一版里「点大圈扇区」与「点返回按钮」都能让中圈消失，但在状态上不是一回事。
用户原话是「点大圈就直接变成别的大类」，所以定稿：

| 动作 | selFamily | selSub | 盘的状态 | 语义 |
|---|---|---|---|---|
| 点任一扇区（闭合态） | → B | → null | 闭合 → 展开 B | 进入下一层 |
| 点任一扇区（展开态） | A → B | → null | 仍展开，换 A 层的中圈内容 | **同级换类** |
| 点「← 重选大类」 | → null | → null | 展开 → 闭合 | **降一层** |

**不给 `paint()` 加 `returning` 中间态**：层级只由 `selFamily` 一个值决定，
动画类是它的派生结果（见第三节）。加一个中间态会让「层数」有两个来源，
而这两个来源在快速连点时必然不同步。

### 二、大圈退到 `.30` 幽灵态，而不是 0

这是本轮唯一与用户原话冲突的地方，必须记清楚：「大圈播放消失动效」与
「在中圈里点别的大类直接切换」互斥 —— 看不见的扇区点不到。用户明确选了
「退到幽灵态但保留可点，悬停浮回」。

`.30` 不是随手挑的：`_wheel7.css` 里六族本色是 3% 饱和的极浅色，`.16` 时
六段读成一条连续灰环（D39③ 的原话），`.30` 是仍能数出六块分界的下限。
悬停 / 键盘聚焦浮回 `1`，当前大类恒为 `1`（它是「我从哪儿进来的」）。

**文字不跟着淡**：把它淡到 `.45`（≈ #9a9a9a on 白，2.9:1）读不清，淡到 `.78`
又和满亮看不出差别 —— 中间没有一档既"退让"又不伤可读性。色块退到 `.30`
已经足够表达"这一层退后了"。换层时给文字一次 300ms 的 opacity 呼吸（1 → .55 → 1），
只动 opacity 不动 transform：`.disc-sector` 的 transform 已被 `translate(-50%,-50%)`
占用，再碰它就会像 D39④ 那样把标签推出弧段。

### 三、退场必须有节点可动

旧实现 `buildSubRing(null)` 里一行 `subRing.innerHTML = ''` 把七段立刻抹掉。
**「返回时中圈播消失动效」在实现层面根本不存在**，CSS 里写多少 keyframes 都没有
东西可以动 —— 这是本轮最先要修的一件事。

改成：先挂 `.is-exit`（CSS 按 `(n−1−i)` 反序收），420ms 后再清。
420 = 220ms 动画 + 7 段 × 22ms 的最长错峰 + 60ms 余量。定时器要能被下一次
`buildSubRing` 掐掉，否则用户在 420ms 内把大类点回来时，定时器会把刚建好的
新节点一起删掉（已用 300ms 内重点的用例验过）。

### 四、动画类只在"层数真的变了"时挂

`paint()` 由 hover 高频调用（每划过一块扇区一次）。写成"每次重绘都重挂"
就等于每划过一次整盘闪一遍。所以：

```js
if (wasOpen !== null && wasOpen !== open) { /* 挂 is-lifting / is-returning，780ms 后摘 */ }
wasOpen = open;
```

**不用 transitionend 做状态机**：测试桩只调监听器、不派发事件，写成状态机会让
`test-render` 的断言链永远停在中间态（D39④ 同因）。动画只负责好看，
状态由 `selFamily` 这一个整数/字符串决定，测试可复现。

### 五、中圈读不出"一片片"是几何问题，不是动画问题

进场动画再好，进来的是"一个白环"就白做。实测（1440 / 900 两视口截图一致）：
七段弧 `#ffffff`、盘心 `#ffffff`、家族环 `#e7ebf5` —— 中圈整条带读成
「一个白环 + 几道灰辐条」。三处一起改：

1. 槽底从 `#b4bcd2` 压到 `#97a3c1`（与白瓦 1.9:1 → 3.0:1）
2. 缝从 2.6° 加宽到 3.4°（520px 盘上 6px → 8px）
3. 槽比弧带每侧再宽 2.4 单位，于是缝里与上下两侧露出的都是槽底

另外弧带内径 114 → 118：盘心半径 110.4，原来只差 3.6 单位（约 4px），
白瓦贴着白盘心，两者并成一块白饼 —— 这是「读不出是浮起的一片片」的直接原因，
不是段数不够。

### 六、窄屏两行标签：判据必须用字形框，不能用按钮盒

360 视口盘心与大圈之间只剩 310px，两行 44px 高的标签必然相交。

## D41 · v15：大圈真消失 + 中圈同步放大、确认改为点击、32 枚图标整批重绘

用户本轮四条修正原文：「一、大圈切换到中圈时，大圈需有明确的消失动画特效，中圈需同步放大过渡，二者不可缺失；二、中圈确认后，箱型选择应由左键点击确定，而非鼠标悬停或拖动位置决定，只有再次左键点击其他箱型时才切换；三、所有小图标需完全重新绘制设计，不得在原有图标基础上修改；四、优化确认后的反馈与视觉设计，使状态变化更清晰、更有层次感。」

### ① 大圈幽灵态（D40）被判不合格，改为真消失

D40 把大圈在展开态压到 `opacity: .30`，理由是「盘还在，还能点」。这一轮实测推翻了它：

| 指标 | 闭合态 | 幽灵态 .30 | 强制 1.0 |
|---|---|---|---|
| 六族填充 L* 极差 | 7.98 | **5.14** | 5.78 |
| 环向 L* 跳变数（r=212 一圈 720 点） | 61 | **19** | — |
| citrus 填充 | `#f8f9e7` L*97.44 | `#f6f6f1` L*96.8 | `#f8f9e7` |

`opacity .30` 把六族色相一起抹掉，六块退成同一种冷灰，只剩描边与缝可分。用户说的"明确的消失"恰好不可能用"变淡"实现 —— 半透明既不像消失，又毁掉了可辨性。

定稿：**展开态大圈 `opacity: 0`，`pointer-events` 保持 `auto`，hover / 键盘聚焦 / 盘心正在讲的那块浮回 1**。消失与可点是两件独立的事。

实测（rAF 逐帧，1440×900）：`1.00 → .85(95ms) → .54(178ms) → .30(261ms) → 0(344ms)`，`fanVanish` 300ms + `--i×18ms` 错峰。

两个实现陷阱，都实测过：
- `.wheel.is-lifting .sector-g` 的 `animation: … both` 会把 opacity 钉在终帧 0，普通声明 `opacity: 1` 压不过 animation —— hover 只升到 `.55`（transition 与动画插值打架）。必须在 hover 规则里显式写 `animation: none`。
- `_wheel6.css:96` 还有一条 `.wheel.is-open .sector-g.is-hot:not(.is-on) { opacity: .55 }`（v6 的"半亮"档），特异度 5 个单位，会继续压着 hover。补写同档 `:not()` 版本才真正回到 1。

### ② 中圈同步放大

`.sub-ring` 是整个 HTML 容器，从 `scale(.58)` 长到 `1`（`ringGrow` 420ms）。58% 时弧带落在半径 68–88，正好是盘心原先盖住的那圈 —— 视觉上是"从盘心里长到它该在的位置"。

**必须在容器上做 scale，不能逐段做**：逐段各自动 scale 会各绕自己的包围盒放大，七段互相穿插成七块错位的瓦。

`transform-origin` 用 `50% 50%` 而不是 `240px 240px`：这是 HTML 容器不是 SVG 图元，`transform-box: view-box` 在无 SVG 布局框的元素上等价 `border-box`，而 border-box 下 240px/240px 相对左上角 —— 520px 控件时圆心在 260px，用 240 会让整条弧带放大过程中向左上偏 20px（截图可见）。

### ③ 确认改左键点击，悬停不再改状态

`paint()` 里 `focusSub` 从 `hovSub || sub` 改成 `sub`。悬停只挂 `.is-hot`（描边加深 + 极轻填充），不改盘心主词、不挂 `is-picked`、不写 `selSub`。

同时修掉一个隐患：hover 驱动 `paint()`，而 `paint()` 会被高频调用；一旦 hover 改状态，盘心文字就跟着指针抖。

`test-render.mjs` 里原来的「悬停某一段后盘心画出标本」随之反转成四条新断言：悬停不改主词、悬停不画标本、悬停不挂 is-picked、悬停只挂 is-hot。这是**断言跟着契约改**，不是放宽。

### ④ 确认后的反馈加三样

- `.hub-kicker` 前一枚 12px 实心小勾（CSS 双渐变拼的，不用图标字体，离线可用），kicker 转 `--blue`；
- `.hub-zh::after` 从 1px 发丝线换成 2px 实心短划 + 68% 宽（预览态仍 54% 且 `opacity: .5`）；
- `.sub-g.is-on` 弧段一次 `arcConfirm` 520ms 脉冲（`drop-shadow` 由 0 → 10px → 6px），不循环 —— 让"点下去"与"指着看"在时间维度上也分得开。

特异度陷阱：`.wheel.is-open.is-picked .disc-hub .hub-kicker { color: var(--ink-3) }` 是 3 类 + 1 类，只写 `.wheel .disc-hub.is-picked .hub-kicker`（3 类）会输，实测 kicker 仍是灰的 `rgb(97,97,97)`。

## D42 · v16：动画链路重做 —— 标签残留、逐级拉出、可见放大、按下态

v15 的进出场在数据上成立、观感上不成立。本轮用 CDP 逐帧采样把每一层拆开量了一遍，四处名不副实的地方全部有实测证据：

### ① 大圈「退场」只退了色块，六个家族标签一个没动

| 时刻 | 0ms | 200ms | 400ms | 870ms |
|---|---|---|---|---|
| `.label-layer` opacity | 1.00 | 1.00 | 1.00 | **1.00** |
| `.sector-g` opacity | 1.00 | 0.52 | 0.00 | 0.00 |

根因是覆盖链：`_wheel4.css:37` 写 `.wheel.is-open .label-layer { opacity: 0 }`，但 `_wheel7.css:361` 又写回 `opacity: 1`（v7 为了让"缩小的盘还能点"把标签显回来）。后者加载更晚、特异度相同，于是赢。v15 只在窄屏媒体查询里盖回去，**桌面端从来没有标签退场**。

### ② 中圈「放大」数据成立、观感不存在

v15 的 `ringGrow` 确实是 `.58 → 1`，但同一 keyframes 里 `60% { opacity: 1 }` 让它在 252ms 就全亮 —— 先亮完、再慢慢变大。人眼对亮度的积分远快于尺寸，整段被读成「淡入」。

**第一轮改完仍不达标**：用户反馈"中圈没有扩大的动效、没占据原来大圈的位置"。量了一下，问题不在动画而在**终点值**：

| 中圈容器 scale | 弧带落点（单位） | 弧带占盘直径 | 结果 |
|---|---|---|---|
| 1.00 | 99–155 | 68% | 大圈退场后外侧空 32%，读成"缩在中间" |
| 1.20 | 119–186 | 79% | 仍偏内 |
| 1.35 | 134–209 | 88% | 标签撞盘心 2 处 |
| **1.43** | **142–222** | **94%** | 中线 192.5 ≈ 大圈中线 193，0 处相交 |
| 1.55 | 154–240 | — | 越出家族环内沿与盘边 |

参考：大圈带 158–228（外径占盘直径 95%），盘心 r=110。

所以终点从 `1` 改成 **`1.43`** —— 这是"弧带中线落在大圈中线"的那个值，也是 0 处相交的最小值。起点相应从 `.52` 改到 `.40`（保持 3.6 倍的行程），过冲从 `1.045` 提到 `1.49`。

实测曲线（1440×900，rAF 每帧）：`0.40(8ms) → 0.66(84) → 1.373(168) → 1.482(251) → 1.49(335) → 1.431(419) → 1.43(502)`。

**摘类跳帧的陷阱**：动画末帧是 1.43，而 `_wheel9.css` 的静态值 `is-open .sub-ring { transform: scale(1) }` 还是 1 —— 700ms 摘类那一刻会从 1.43 缩回 1，肉眼可见地弹一下。静态终态必须跟着改成 1.43（本轮已改，并加了断言守着）。

**窄屏连带修正**：整体放大 1.43 之后，v15 把中圈标签外移到 152 单位（`SUB_LABEL_R_NARROW`）会被推到 217 单位、越出盘外（实测 360 视口 3 处 outBox）。收回 120：360 视口下中心 111.5px、四字右缘 143px，盘半径 156px 留 13px 余量，内沿 80px 仍在盘心半径 72px 之外。四视口复测 outBox 全归零。

### ③ 确认反馈只有一层 `filter: drop-shadow`，520px 盘上不可见

探针每帧都在变，但 `arcOp` 恒 `1.00`、没有任何几何变化 —— 没有位移就没有"按下"。改成绕盘心的整段缩放 `1 → 1.032 → 1`（520ms），在 r≈135 处产生约 4.3px 径向位移，可读且不推乱相邻段的缝。

### ④ 「按下态」在 v15 里根本不存在

`:active` 只在真实指针按住时生效：键盘 Enter、脚本 dispatch、触屏滑动取消三种情况全漏。改成 JS 挂的显式类 `.is-pressing`，由 `pointerdown` 挂、`pointerup` / `pointercancel` / `pointerleave` / 全局 `pointerup` / `blur` / `chooseSub` 六处摘。

按下量也因此要足够：`.955` 只让包围盒从 62.4px 缩到 59.6px（−4.5%，1x 下 2.8px），肉眼几乎看不出；改 `.93`（−7.1%，4.4px）再叠描边 `1px → 1.6px` 收紧 —— 人眼对边界的位移比对亮度更敏感。

### 三个实现陷阱（都实测踩到）

1. **`animation: … both` 会把属性永久钉在末帧**，普通声明压不过它。v15 的 `fanVanish both` 钉住 opacity（hover 只升到 .55）；v16 的 `arcFadeRise both` 钉住 transform（按下态 `scale(.93)` 完全无效，`matrix(1,0,0,1,0,0)` 一动不动）。修法：把按下态的 transform 挂到 `.sub-g`（无两者的父层），并给 `arcPop` 去掉 `both`。
2. **`transform` 写进 keyframes 必须把基类的三段一起写**。`.disc-sector` 的基类是 `translate(-50%,-50%) rotate(calc(-1 * var(--disc-rot, 0deg)))`；只写 `scale()` 会把居中覆盖掉，标签每帧被推到右下再弹回；漏掉 `rotate(calc(-1*var(--disc-rot)))` 则圆盘拖拽后文字跟着歪。
3. **`will-change` 不能写在常驻类上**。`.sub-g.is-on` 是确认后一直挂着的类，写在那里等于让那一段永久独占合成层，反而拖慢同盘其它动画。只写在带动画的临时类上（`is-lifting` / `is-returning` / `is-pressing`），类 700ms 后摘掉即释放。

### 编排定稿（两拍结构）

用户的原始要求是"6 个标签先各自散去，全部结束后大圈容器整体渐隐"。v15 把扇区也做成逐块错峰、与文字并行，读起来是"扇区和字一起往下掉"。v16 拆成两拍：

| 拍 | 元素 | 动作 | 时长 / 缓动 / 延迟 |
|---|---|---|---|
| 进·1 | 6 个家族文字 | 缩 .90 + 反旋 +3° + 淡出 | 240ms `(.4,0,.9,1)`，`i×26ms` |
| 进·2 | `.label-layer` | 散净后整层归零 | 160ms linear，**370ms** |
| 进·3 | 6 个 `.sector-g` | 整盘缩 .94 + 淡出 | 200ms `(.4,0,.95,1)`，**370ms** |
| 进·4 | `.sub-ring` | `.52 → 1.045 → 1` | 460ms `(.16,1,.3,1)` |
| 进·5 | 7 段弧 | 淡入 + −2° 回正 | 300ms linear，`100+i×28ms` |

实测消失时刻：`label0 165ms → label5 298ms → sector0/5 499ms`（两拍分得开）。

返回按「中圈 → 弧段 → 扇区 → 文字」由内向外，延迟 100 / 180 / 240，间隔 80/60ms（越靠外越短，读成扩散而非排队）。实测首次达 50% 的时刻：`arc 0 → layer 138 → sector0 221 → label0 272 → sector5 320 → label5 371`。

## D43 · v17：滞后边框的三层成因 + 结构分层修正

用户报两件事：①点击大类后「会出现一个大圈边框，要过一会儿才消失」；②整体布局、线条细节需要精修。

### 一、滞后边框：逐帧截图定位到三层成因，都是同一个错误的三种表现

用 CDP 在 0/80/160/240/320/420/540/700/900/1200ms 各截一帧，沿 45° 方向逐像素扫亮度。逐层排除：

**成因 A：`.sub-channel` 从第一帧就全亮。**
它是 `buildSubRing()` **新建**的节点 —— 插入 DOM 那一刻父级上的 `is-open` 已经在了。于是第一帧同时算出 `opacity: 0`（基础规则）与 `opacity: 1`（is-open 规则），浏览器只认后者，**transition 没有"前一个值"可过渡**。实测：闭合态 `document.querySelector('.sub-channel')` 返回 `null`（DOM 里根本没有），点开之后立刻读 computed opacity 就是 `1`。

修法：改用 `animation: channelIn 140ms linear 130ms both` —— animation 不依赖前值，插入即播。实测曲线变成 `0.00(10ms) → 0.00(92) → 0.14(176) → 0.74(259) → 1.00(342)`。

**成因 B：扇区的 `animation-delay` 期间被 `both` 钉在全亮。**
v16 第一版写 `animation-delay: 370ms` 想让"文字全散完再收整盘"。但 `both` 填充意味着**延迟期间保持 0% 帧的值**（opacity 1）。于是 0–370ms 那圈 158–228 的家族环全亮挂着，中圈已经在长了。改成 `delay: 0ms` + 150ms 时长：
`opacity 1.00(7ms) → 0.83(69) → 0.30(136) → 0.00(202)`。

**成因 C：文字链太长，把 A/B 都盖不住。**
原 `labelVanish 240ms + i×26ms`（最长 370ms），加扇区 200ms = 570ms。压到 `180ms + i×12ms`（最长 240ms），整条退场链 570 → 260ms。

三层都修完之后，120ms 那一帧：大圈 0.14、槽底 0.14、弧片 0.17 —— 三者同步。

**教训一句**：`animation ... both` 会把延迟期间也保持首帧值。凡是"延迟播放"的退场动画，延迟本身就是留一段"仍然全亮"的时间。

### 二、结构分层：两个量出来的问题

| 项 | 实测（1440 视口，盘 520px，R=260） | 问题 |
|---|---|---|
| 家族扇区外沿 | 247px（r1o=228 单位 × 1.083） | — |
| `.wheel::after` 轮廓线 | **235px**（inset 4.9%） | **画在扇区里面 12px** |
| `.ring-thin` SVG 线 | 256px（r1o+8=236 单位） | 落在盘外 |
| 盘心半径 | 119.5px | — |
| 盘心到弧带内沿 | 183 − 119.5 = **63px** 纯白 | 一整圈空洞，读不出层级 |

轮廓线那 12px 是 v11 写 `inset: 4.9%` 时的遗留（那时家族环还缩放），v9 取消缩放后没跟着改 —— **闭合态就能看到六块色环外沿是裸的毛边**。

修：轮廓 `inset: 4.9% → 1.75%`（251px，扇区外 4px），`.ring-thin` 直接 `opacity: 0`（它的职责被真轮廓接管）。轮廓与扇区之间那 4px 空隙做暗线+亮线倒角，盘才有厚度。

63px 空洞补一道**分层刻线**（`.sub-ring::before`，最终半径 170px），标出中圈内沿，与盘心发丝线呼应，形成「盘心 → 刻线 → 弧带 → 盘沿」四段节奏。

### 三、复用一个 `display:none` 的伪元素踩到的三个坑

`.sub-ring::before` 是 v5 的虚线轨道（v7 起 `display:none`），复用它踩了三次：

1. 它有 `left:50%; top:50%; width:75.2%; height:75.2%` —— 只写 `inset` 会被这些属性干扰，实测 computed `inset` 变成 `140.9px`（由 left/top 反算），`27.1%` 完全没生效。改成四条独立属性 + `transform: none`。
2. `_wheel7.css:338` 有 `.wheel.is-open .sub-ring::before { display: none }`，比 `.wheel .sub-ring::before` 多一个类。必须用同档选择器重新 `display: block`。
3. **`inset` 百分比相对未缩放容器算**，最终半径还要乘容器的 1.43。想要最终 170px：`260 × (1−2X) × 1.43 = 170 → X = 27.1%`。第一版按未缩放反算成 14.8%，乘 1.43 后跑到 262px、落在盘沿外面，截图里什么也看不到。

### 四、验收

- 四视口 × 全 6 族 × 全 32 子项：`overlaps=0 / clipped=0 / outBox=0`；弧带落点 1440 为 137–246、窄屏 141–247。
- 四套测试 286 项全绿（`test-render` 136，新增 1 条守「扇区 delay 必须 0」+ 1 条守「凹槽必须用 animation」）。
- `_wheel11.css` 为本轮新增层。

## D44 · v18：中圈选定后 hover 必须完全失效（两个反馈 bug 的共同根因）

用户报两件事：①（截图）选中「香草甜」后，指针划到「酒香」上，那一块出现了蓝色描边框；②在同一块内移动鼠标会闪动，边框被反复触发。

### 根因：hover 有两条并行通路，只挡了一条

中圈 `hover` 的视觉反馈走**两条互不知情的路**：

| 通路 | 实现位置 | 谁控制 |
|---|---|---|
| **JS 通路** | `enter()/leave()` 写 `hoverSub` → `paint()` 给 `.sub-g` 挂 `is-hot` | `app.js` |
| **CSS 通路** | `.wheel .sub-g:hover .sub-arc { … }`（`_wheel7.css` 12 处） | 浏览器，**JS 看不见** |

v15 那句注释写的是「hover 只给视觉提示，不改任何状态」—— 它只改了 JS 那条路（不再写 `selSub` / 盘心主词），**CSS 那条从来没人管**。所以 `is-hot` 确实没挂（实测 `cls: "sub-g"`），但 `.sub-g:hover` 照样命中，描边从 `1px` 变 `1.4px`、填充从 `url(#gArc)` 变 `rgba(255,255,255,.92)`、`g` 上加一层 `drop-shadow`。

实测（1440，选中第 1 段后把指针移到第 3 段）：

| 状态 | class | stroke-width | fill |
|---|---|---|---|
| 选中后常态 | `sub-g` | 1px | `url("#gArc")` |
| 选中后 hover | `sub-g`（**无 is-hot**） | **1.4px** | `rgba(255,255,255,.92)` |

图片里那道蓝框就是这么来的：它是 `.sub-arc` 的 `stroke` 变粗变深，不是任何选中态。

### 闪动的第二个原因：两个 hover 入口互相取消

弧段（SVG `g`）和它上面的文字（HTML `button`）是两棵子树，各自绑了 `mouseenter/mouseleave`，都写同一个 `hoverSub`：

```js
const enter = () => { hoverSub = item.id; paint(); };
const leave = () => { if (hoverSub === item.id) { hoverSub = null; paint(); } };
```

指针从弧段移到文字上时，`g` 的 `mouseleave` 先触发、把 `hoverSub` 清空，紧接着 `button` 的 `mouseenter` 又设回来 —— 同一段内来回移动就会反复触发 `paint()`。实测在同一段内来回 6 次，`.sub-g` 的 class 变更 **11 次**。这就是"闪动"。

### 修法：两条通路一起挡，用同一个锁

**JS 守卫**（挡通路 1，顺带解决闪动）：

```js
const enter = () => { if (selSub) return; hoverSub = item.id; paint(); };
const leave = () => { if (selSub) return; if (hoverSub === item.id) { hoverSub = null; paint(); } };
```

`selSub` 有值就整个 return —— 既不写 `hoverSub`（不挂 `is-hot`），也不调 `paint()`（不重绘、不闪）。`click` 不经过这两个函数，切换照常。

**CSS 锁**（挡通路 2）：`paint()` 里维护 `root.classList.toggle('is-sub-locked', !!selSub)`，`_wheel7.css` 里全部 8 处 hover 规则改写成：

```css
.wheel:not(.is-sub-locked) .sub-g:hover { … }
.wheel:not(.is-sub-locked) .disc-sector.lvl2.sub-arc-btn:hover { … }
```

为什么不直接删 hover 规则：未选中时它仍是必要的"哪里能点"的提示（D41 明确要求保留）。它不该被删，该被上锁。

### 验收（CDP 实测）

## D46 · v21：取消人为数据上限（400 → 1228），以及为什么不需要向量库

用户的要求是"取消人为设置的上限"。查下来这个上限从头到尾都是我们自己的 `--limit`，不是数据源的。

### 数据源的真实容量

| 环节 | 条数 | 说明 |
|---|---|---|
| 上游快照（本地 `data/source/perfumes.upstream.jsonl`） | 1320 | 2026-10-21 快照 |

| 家族映射不上被拒 | 0 | 全部映射成功 |
| **合格** | **1228** | — |
| 旧 `LIMIT` 默认值 | 400 | **人为截断，没有技术理由** |

上游仓库 README 现在声称 1,479 行（2026-10-27 快照），比本地快照多 159 条。**本轮没有同步这 159 条**：本机到 `raw.githubusercontent.com` 的直连是 `ECONNRESET`（node https 与 curl 都失败），只能通过抓取工具取回，而抓取工具会把 1.5MB 结果截断到 199KB（约 397 行）。用截断数据覆盖上游等于**数据倒退**（我实际误覆盖了一次，已 `git checkout` 还原并校验为 1320 行）。这 159 条列为待办，不是已完成的。

### 决定：`--limit` 默认改为不截断

```js
const LIMIT = (() => {
  const i = process.argv.indexOf('--limit');
  if (i < 0) return Infinity;
  const n = parseInt(process.argv[i + 1], 10);
  return Number.isFinite(n) && n > 0 ? n : Infinity;
})();
```

配套改了三处：`MIN_PER_FAMILY` 在 Infinity 下退化为固定 12（原式 `Math.floor(Infinity/12)` 会变成 Infinity，语义混乱）；第三轮兜底在全量模式下即"全收"；`slice(0, Infinity)` 需换成条件写法（`slice` 传 Infinity 其实等价于全取，但显式写更清楚）。

### 性能实测：千级条目不需要任何加速结构

| 库容 | 单次 `recommend()` |
|---|---|
| 1,228 | **8.8 ms** |
| 3,684 | 22.1 ms |
| 9,824 | 49.6 ms |

线性增长，万级仍在 50ms 内（人眼阈值约 100ms）。**这就是不做向量库的第一个理由**。

### 为什么不做向量数据库（三条理由，按重要性排）

1. **产品原则不允许。** `PRODUCT.md` 第二条是"理由必须可反推出某个答案"。向量相似度只能给"相似度 0.83"，给不出"因为你要偏凉、它甜度 0.07、且含你点名那瓶里的佛手柑"。用了向量检索，这个项目最核心的差异就没了。
2. **性能不需要。** 见上表，规则打分在万级仍是毫秒，没有"检索太慢"这个问题。
3. **运维成本不成比例。** Milvus / Qdrant 需要常驻服务与持久化，破 D05「零构建、`node server.js` 就能跑」。一个静态页为了 1228 条数据挂一个数据库服务，代价远超收益。

**"数据能持续扩充"这个需求是对的，但解法和向量库无关**：正确的载体是 `scripts/build-data.js` 这条离线管线 —— 换数据源、加去重、加校验、重跑，产物仍是静态 JSON。

### 连带修掉的假话

页脚与 README 里原有三处硬编码"只收录了 400 瓶样本"。数据变 1228 之后这三处全部失真，已改为不写死数字的表述（"库容随上游开放数据集更新"）或写当前实测值。**这类数字一改就会变成假话，所以能不写死就不写死。**

## D53 · v26：深色模式（D4）—— 不是把白纸翻黑，是把明度轴反向后重排

### 一、改哪些、不改哪些：清点 96 处写死色值

### 二、明度轴的方向不是全局反转

浅色的三层是"白纸 → 浅灰 → 中灰"，越大越深：

```
浅色： --bg #ffffff → --bg-2 #f5f5f5 → --bg-3 #e8e8e8
深色： --bg #141414 → --bg-2 #1e1e1e → --bg-3 #2a2a2a
```

`--bg-3` 在浅色里**比 --bg 深**（#e8e8e8 压白），在深色里**必须比 --bg 亮**（#2a2a2a 提黑）。它的语义是"更平/更凹的底"（禁用底、未完成进度），方向跟着底色走，不是跟着数值走。照抄数值会让它读成"比背景更凹陷"。

### 三、对比度必须按深底重算，不能照搬

|---|---|---|
| `--ink` | `#f2f2f2` | **15.9** |

| `--ink-3` | `#a3a3a3` | **6.0**（与浅色版 6.19 同档） |

### 四、三个"照抄会翻车"的地方（全部实测踩到）

#### 4.1 三级描边不能整体提亮

### 五、六族渐变：深色版是重新定色，不是压暗

## D54 · v27：佣金链路的现实约束，与「搜索兜底」这一层

### 一、先说结论

K1（三件套参数）与 K2（商品页地址）**都不是"给我三个值"就能解决的**。
它们在纯静态、零后端、无账号的前提下，受三个外部事实限制：

1. **联盟注册需要实名与审核**，不是填个表就出 PID。
2. **电商搜索页与商品页在无登录态下都先弹登录**（实测，见下）。
3. **联盟转链需要服务端签名或后台操作**，不是一个可以写死在常量里的 URL 模板。

所以本轮**不做**"假装接上了佣金"，而是把链路拆成三档能真实工作的形态：

| 档 | 触发条件 | 是否带佣金 | 是否标 sponsored | 是否挂「广告」披露 |
|---|---|---|---|---|
| `direct` | `target` + `pid` + `productBase` 三件套齐备 | 是 | 是 | 是 |
| `link` | `data/affiliate-links.json` 里有这一瓶的直达页 | 否 | **否** | **否** |
| `search` | 只配了 `platform`（默认就有） | 否 | **否** | **否**，改说"这是搜索结果页" |

`direct` 的代码路径（`affiliateHref`）与 v25 完全一致，一行没改 ——
它等的就是那三个值。新增的是下面两档。

### 二、实测：为什么"直接跳到商品页"这条路走不通

用 Edge headless（1440×900，无登录态）逐个访问，2026-11-01 实测：

| 目标 | 结果 |
|---|---|
| `https://search.jd.com/Search?keyword=Creed Aventus` | 302 → `passport.jd.com/new/login.aspx?ReturnUrl=…` |
| `https://so.m.jd.com/ware/search.action?keyword=…` | 302 → `plogin.m.jd.com/login/login?returnurl=…` |
| `https://s.taobao.com/search?q=Creed Aventus` | 停在原地，正文"亲，请登录"，商品区"加载中…"永不完成 |
| `https://list.tmall.com/search_product.htm?q=…` | 302 → `s.taobao.com/search?fromTmallRedirect=true…`，同样要登录 |
| `https://item.jd.com/100012043978.html` | 302 → 登录页 |
| `https://item.taobao.com/item.htm?id=…` | 302 → `login.taobao.com/havanaone/…` |

**结论**：搜索页与商品页都需要登录态才能看到内容。但这不构成阻塞 ——
真实用户在自己的浏览器里是登录着的，链接打开就能用。
真正受影响的是"服务器端去抓商品页来匹配到具体某一瓶"，那条路要登录态，走不通。

`pub.alimama.com` 的首页正文长度是 **1**（只有一个字符 `X`），
真实内容全在 `login.taobao.com` 的 iframe 里；`/register.htm` 直接 302 到
`login.taobao.com/havanaone/login/login.htm`。即**没有"匿名可读的注册表单"**，
注册必须先有淘宝账号。

三家平台的注册入口实测：

| 平台 | 入口 | 需要的账号 | 可见字段 |
|---|---|---|---|
| 淘宝联盟 | `pub.alimama.com` → 内嵌 `login.taobao.com` iframe | 淘宝账号（实名） | `fm-login-id`（账号/邮箱/手机）、`fm-login-password`、图片验证码、协议勾选 |
| 京东联盟 | `union.jd.com` → "账号登录/扫码登录" | 京东账号（实名） | 页面无输入框，登录态在 `passport.jd.com`；文案"京东账号登录即可开始推广" |
| 多多进宝 | `jinbao.pinduoduo.com` 首页浮层 | 手机号 + 短信验证码 | `#mobile`、验证码输入框、协议勾选 |

三家都**不提供"注册即得 PID"**：先有电商账号 → 申请联盟 → 审核 → 后台建推广位 → 才有 PID。

### 三、为什么保留搜索兜底，且它不挂「广告」

在 `direct` 拿不到参数之前，页面上一个购买入口都没有 —— 这不是"以后再做"，
而是当下就没法用。搜索跳转不需要任何注册，只是替用户少打一次字。

**关键取舍：搜索链接绝不标 `sponsored`、绝不挂「广告」披露。**
- 它没有商业关系，标 sponsored 是对搜索引擎和用户的**双重虚假标注**。
- 「广告」披露一旦贬值（到处都写），真正需要它的时候就不显眼了。
- 反过来，搜索链接**必须**说明"这是搜索结果页，不是这一瓶的商品页" ——
  用户点进去发现不是商品页而没有这句话，就是一次欺骗。

所以 DOM 层把两种说明分开：广告披露走 `.aff-note`，
搜索说明走 `.link-note`。实测踩过：两者共用 `.aff-note` 时，
测试数 `.aff-note` 得到 3，分不清是广告还是搜索说明（`m06913`）。

### 四、视觉分层：搜索链接必须比"能买"轻一档

`direct` 是实心蓝底 + 白字（"点这里完成这件事"）。
搜索跳转完成的不是"买到这一瓶"，用同样的实心蓝等于把两件不同分量的事说成一件。
所以 `.buy-link.is-search` 改成：描边 1px `--stroke-ui`（D1 的 3:1 达标色）+
文字 `--blue` + 透明底 + `font-weight: 500`（不加粗到 600）。
悬停才给 `--blue-wash` 底。配色全部走既有变量，未新增色值。

### 五、阶段二：`data/affiliate-links.json` 接口已就位

`ensureAffLinks()` 在 `boot()` 里预热（不阻塞首屏），文件结构：

```json
{ "platform": "jd", "generatedAt": "2026-11-01", "links": { "<perfume.id>": "https://item.jd.com/xxx.html" } }
```

- 文件不存在 / 解析失败 / `links` 为空 → 三种情况一律 `AFF_LINKS = false`，
  静默退回 `search`，**绝不阻塞任何现有功能**。
- 表里的 URL 会过 `new URL()` 检查协议，`javascript:` 等非 http(s) 被拒并退回 `search`。
- 生成脚本 `scripts/gen-affiliate-links.mjs` 是**可选工具**，密钥只从环境变量读、
  不写进任何入库文件。

比例说明：`AFF_LINKS` 用 `null` 表示"还没试过"、`false` 表示"试过、没有"，
这样重复调用不会反复发请求，也不会把空对象当成功。

## D55 · v28：`matchPct` 的分母（G6）—— 修的是"天花板"，不是"公式"

### 一、原问题

`src/scoring.js` 的 `matchPct = score / maxPossible`，分母是
`Object.values(WEIGHTS)` 全部正项之和 = **275**。这个数**不是可达上界**：

- `family` 因子（`emotionFamily` 30 + `occasionFamily` 22 = 52）内部是
  `clamp01(famHit / 1.2) * 52`。只选一族时向量点积最高 1.0，除以 1.2 只剩 0.833，
  这一项**永远拿不到 52，实测全库最高 44.8**。
- 于是"每项都满分"的假想瓶也只有 241.5 / 275 = **88%**。
- 真实答案更远：七步全答的第 1 名原始分约 190，显示 **69%**。
  **一个近乎完美的匹配被显示成 69%。**

### 二、四个候选口径的实测（`scripts/probe-matchpct.mjs`）

40 组随机答案 × 10 个答题深度，第 1 名 `matchPct` 中位数：

（`node scripts/probe-matchpct.mjs` 的输出，2026-11-01 复跑核过）

| 深度 | 答了什么 | A 现状 /275 | C /已答权重 | F /库内可达 | G 收缩修正 |
|---|---|---|---|---|---|
| 0 | 只点香型 | 36% | **90%** | **100%** | 62% |
| 2 | +场合 | 38% | 87% | 92% | 68% |
| 4 | +季节 | 45% | 83% | 89% | 76% |
| 6 | +气质 | 55% | 78% | 83% | 80% |
| 8 | +情绪/小类 | **69%** | 81% | 86% | 86% |

**关键发现：A 的数值失真但方向对（36%→69% 单调递增）；
C 与 F 的数值"合理"但方向错（只点一个香型就 99%）。**
只答一题却标 100%，比答十题标 69% 更糟 —— 前者是虚假承诺。

### 三、采用：可达上界 + 证据门槛

**分母**改成「本次答案的逐因子库内可达之和」（`tightBound`）。
它一定 ≥ 任何单瓶得分（每瓶每项都不会超过该项的库内最高），所以
百分比不会超过 100%，且 100% **是真能到的**。

**但**分母随答案变会让"答得少反而高"，所以配一道证据门槛：

## D57 · v30：佣金链路改走联盟开放平台 API ——「只能手工复制短链」这个结论被推翻

### 一、推翻的到底是什么

D54 与 `docs/AFFILIATE-SETUP.md` 都写过：

> 京东给的是每瓶一条独立短链，不是可以套模板的参数化链接。所以「1228 瓶全部自动接上佣金」做不到 —— 只能一瓶一瓶拿链接。

这句话在**手工路径**下成立，在 **API 路径**下不成立。两家的联盟后台都提供
关键词搜索接口，能按「品牌 + 香名」召回商品，再换推广链接：

| 平台 | 搜索 | 转链 | 步数 |
|---|---|---|---|
| 京东 | `jd.union.open.goods.query`（keyword → skuId） | `jd.union.open.promotion.common.get`（materialId → clickURL） | 2 |
| 淘宝 | `taobao.tbk.dg.material.optional`（q + adzone_id → click_url） | 同一个接口就返回了 | 1 |

于是「人工过验证码」这件事从链路上消失了 —— 不是因为解决了验证码，
而是因为**根本不需要打开浏览器**。

### 二、顺带否掉的一个方案：Scrapling

用户问「能不能用 Scrapling 过验证码」。核查结果：不能。
阿里妈妈用的是自研 `baxia` 风控，而 Scrapling 的 `solve_cloudflare`
只覆盖 Cloudflare 的 Turnstile / Interstitial 三类挑战。更关键的是，
绕过风控的代价落在**用户自己的联盟账号**上（后台有清退规则）。

判据留下：这类「HTTP 200 但正文只剩一个字符」的页面是登录墙，不是站点失效。
`pub.alimama.com` 未登录返回 200 / 1951 字节 / 正文 `X`，与 D54 记录一致。

### 三、旧 `--api` 分支的三处硬伤（一次全修）

`scripts/gen-affiliate-links.mjs` 的 `--api` 分支写于 v29，从未被执行过
（当时没有凭证），所以三个错误一直躺着：

| # | 旧写法 | 事实 |
|---|---|---|
| ① | 手拼 `md5(secret + "appKey" + key + "materialId" + id + "timestamp" + ts + secret)` | JOS 的签名是对**全部系统参数**按 key 字典序拼串，业务参数整体 JSON 进 `360buy_param_json` |
| ② | appKey / materialId / timestamp 直接摆在 query 上 | 业务参数必须在 `360buy_param_json` 表单字段里，且请求是 POST 表单 |
| ③ | 从 `IN_SOURCE.skus` 读 SKU | 那个字段从来没人写过；改为读 `data/product-skus.json`（自动生成） |

**为什么这次能发现**：拿假凭证跑了一次真实网关，返回的是 `code 21`。
**但注意：`code 21` 不能证明签名正确。** 补测（同一分钟，同一网关）：
把 sign 改成 32 个 0、把 timestamp 改成 2020 年，返回的**同样是 `code 21`**，
连 `en_desc` 一字不差。也就是说京东是**先校验 app_key、后校验签名**，
app_key 不合法时根本走不到验签那一步。

所以这条证据的边界必须写清：它能证明的是 **请求格式（POST 表单 +
`360buy_param_json` + 系统参数）被网关接受并进入了解析流程**，
**不能**证明签名正确。签名正确性只由 `scripts/test-union-api.mjs` 的固定向量保证。

淘宝那一侧的证据强一些：假凭证返回 `29: Invalid app Key`，与签名错的

理由：签名写错**不会有任何提示**，只回一句「签名错误」，而每次错误都真花配额。
又因为上面那条"京东先验 key 后验签"，**本地固定向量是唯一能自证签名正确的手段**。
抽成纯函数后用固定向量钉住（`scripts/test-union-api.mjs`，32 项）：

- S1/S2 两家各一条固定向量（输入确定，sign 必须逐字节相同）

### 二、控件反馈（3-B）

选 3-B 而不是 3-A/3-C 的判据：3-A（只改颜色）会让四类控件给出四种不同物理反馈 —— `.chip` 内缩、`.btn` 下沉、`.choice` 完全没位移；3-C（只加粗描边）在白底灰线上实测亮度差 0.02，等于没反馈。1px 是唯一既能被察觉、又不会在 8 项网格里造成"互相推挤"错觉的位移量。

`:active` 一律用 `translateY` 不用 `scale()` —— scale 会让文字一起变形，1.2% 的压缩在中文字形上表现为"发糊"。主按钮 `.btn` 保留它原有的 `translateY(1px) scale(.988)`：它是全站唯一实心蓝底控件，换掉会与次要按钮同档。

### 三、切屏过渡（2-A + 2-B 按屏混用）

`render()` 写 `app.dataset.scene`，三档 keyframes 挂在 `#app[data-scene=...] .fade-in`：

| scene | 动效 | 时长 | 用在哪 |
|---|---|---|---|
| `cut` | `sceneCutIn` 纯透明度，零位移 | 140ms linear | 香调 / 场景 / 浓度 / 锚点 —— 用户在做选择，位移会打断"连续答题"的线性感 |
| `settle` | `sceneSettleIn` 下沉 8px 淡入 | 260ms `--ease` | 首屏 / 心情 / 整族排除 —— 进入新阶段 |
| `rise` | `sceneRiseIn` 上浮 14px 淡入 | 260ms `--ease` | 结果页专用，位移最大 |

没有做旧屏快照 `.scene-ghost`：`render()` 是整页重建，做克隆意味着 140ms 内 DOM 里存在两份 `.disc-hub` / `.plate-svg`，而 `test-render.mjs` 有 40 余处按类名计数 —— 会直接打红，且这些计数正是"元素不重复"的守门。退而求其次：旧屏瞬消、新屏淡入，观感上是一次带软边的硬切，这本身就是 2-A 想要的效果。

`prefers-reduced-motion` 只写 `animation-name: sceneCutIn` 与 `transform: none`，**不写时长** —— `base.css:1673` 的 `*{animation-duration:1ms !important}` 会盖掉一切时长声明。效果 = 内容瞬间出现、无滑动，反馈仍在（减位移不减反馈）。

### 七、踩坑

1. **`animation` 简写里第二个时间值是 delay，不是 duration**。批量把字面量换成 token 时，`channelOut 120ms linear 90ms both` 这种写法会被正则一把替换成两个 `var(--t-micro)`，结果 delay 变成 120ms、退场反而变慢。第一版就踩到了，后改为**逐条手写、只换 duration 位**，并用"同一条 animation 里不得出现两个 `var(--t-`"作自检。
2. **`autofit` 式的全局替换会打穿语义**：`420ms` 在 `.sub-ring` 上不是"时长档"，是和 JS 共享的数值。凡是"JS 等它、或它等 JS"的时间都必须留在字面量里，并就地写注释说明。
3. **反制块要抄原始值，不要抄"设计意图"**。`.wheel .hub-skip:hover` 把 `border-style` 从 `dashed` 改成 `solid`，反制时必须把 `dashed` 写回去 —— 只写 `border-color` 会让触屏上留着一圈实线边。

| 情绪入口 | **15 / 36**（另 6/36 改变第 1 名） |

### 二、根因

`scent-picker/src/scoring.js` 的候选池逻辑：

```js
const isDominant = (s) => { /* 该瓶的主族 === 用户选的族 */ };
if (profile.family) {
  const L1 = scored.filter(isDominant);
  ranked = L1.length >= topN ? L1 : (L2.length >= topN ? L2 : scored);
}
```

选了家族之后，候选池被过滤成**只有该族主导的瓶子**。实测六个族全是 `10/10 同族`：

| 族 | 主导瓶数 |
|---|---|
| citrus | 117 |
| floral | 533 |
| woody | 243 |
| amber | 191 |
| fresh | 162 |
| gourmand | 142 |

而扣分条件是「该族 = 这瓶的主族」：

```js
const top = fams.sort((a, b) => b[1] - a[1])[0];
const hit = profile.dislikedFamilies.find((f) => top && top[0] === f);
if (hit) { score += WEIGHTS.dislikedFamily; }
```

池子里 100% 都是用户自己选的那一族，排除任何**别的**族都永远打不中。
排除**本族**倒是会全部 −30，但整池同扣等于没扣（实测 top-3 顺序完全不变）。

### 三、为什么不选另外两条路

| 方案 | 实测 | 否决理由 |
|---|---|---|
| 删掉这一屏 | 情绪入口会损失 15/36 的有效能力 | 情绪入口那边是真有用的，不能为了另一个入口的毛病一起删 |
| 放宽扣分到「该族权重 ≥ 0.5」 | 家族入口 10/30 生效 | 会连带改变情绪入口结果（实测 `cold` + 排除 `fresh` 三瓶全换），而情绪侧本来正常工作，没必要动 |
| 改问法（只在家族入口改文案） | 打分不变 | 用户点了一样没效果 —— 是把白问包装得像有用，比露出来更糟 |

### 四、做法

`STEPS` 里给「整族排除」加一个 `when` 谓词，把 `STEPS` 变成全集、由 `curSteps()` 动态过滤：

```js
{
  id: 'dislikedFamilies',
  /* 只在**情绪入口**下出现。
     · 家族入口：30 种组合里 0 种改变 top-3（池子被 isDominant 收窄，扣分打不中）
     · 情绪入口：36 种组合里 15 种改变 top-3、6 种改变第 1 名 */
  when: (a) => !a.family,
}
```

所有读 `STEPS.length` 的地方（`next()` / `finish()` / `renderProgress()` / `renderMasthead()` / `render()` / 数据加载回调）全部改走 `curSteps()`。
`stepHead(id, answers)` 也接受显式 answers，否则测试里两次调用都读 `state.answers`，测不出分叉。

结果：

|---|---|---|
| 家族入口（转盘选了族） | 6 | 不出现 |
| 情绪入口（按感觉选） | 7 | 第 6 步 |
| 未答任何入口 | 7 | 第 6 步（保留全集，不隐藏） |

## D62 · 问卷去冗余：三处「问了等于没问」（v37）

用户问「有没有问过但没起作用的问题」，实测出三处，全部处理。

### 一、第 5 步「你想要多浓」：5 档里 3 档完全无效

| 档位 | 与「不答」的 top-10 重叠 | 判定 |
|---|---|---|
| 1 | 1/10 | 有效 |
| 2 | 4/10 | 有效 |
| **3** | **10/10** | 等于没答 |
| **4** | **10/10** | 与 3 逐瓶相同 |
| **5** | **10/10** | 与 3 逐瓶相同 |

根因在 `src/scoring.js` 的 heaviness 定义：

```js
const heaviness = ((p.families.amber || 0) + (p.families.gourmand || 0)) /
  (Object.values(p.families).reduce((a, b) => a + b, 0) || 1);
```

这是**家族向量**，不是瓶子自身属性。同一族内所有瓶子的分子分母高度相似 ——
实测同族唯一取值 floral 533 瓶只有 23 个、woody 243 瓶 11 个、citrus 117 瓶 6 个。
于是 intensity 只是给整个族加同一个分，族内无法区分。

再叠一个：`scoring.js` 里 `const intensity = Number(answers.intensity) || 3;`
不答就是 3，所以 3 档必然与不答同分。

**改法**：新增 `heavinessOf(p)`，只用瓶内属性：

```js
const byChar = heavy / (heavy + light);   // character 标签的暖/凉比，覆盖 1388/1388
const byConc = CONC_HEAVY[p.concentration] ?? 0.5;  // 覆盖 1142/1388
return byChar * 0.65 + byConc * 0.35;
```

- `HEAVY_TAGS`：warm amber resinous spicy smoky leathery sweet creamy vanilla balsamic musky powdery rich
- `LIGHT_TAGS`：fresh clean green citrusy herbal salty aquatic ozonic soapy aldehydic fruity
- 划分依据是**闻起来重不重**，不是好坏。
- 0.65/0.35 是试出来的：character 单用会让「暖标签多的」和「浓香水」分不开
  （实测皮革烟草与焦糖琥珀极差仅 3.1 分），加浓度后六族极差都回到 3.6 以上。

改后：`floral` 五档与不答的重叠变成 `0 / 2 / 10 / 1 / 1`（第 3 档是中间值，
与不答同分是应有的行为）。族内唯一取值：floral 23→31、woody 11→28、
fresh 9→27、citrus 6→24。

### 三、第 3 步：冷暖与甜度其实是气质的两个分量

七个气质原型的 `dims` 正好是 `temp × sweet × weight` 的 2×2×2：

| 原型 | temp | sweet | weight |
|---|---|---|---|
| 洁净清透 | −1 | −1 | −1 |
| 雨后林地 | −1 | −1 | +1 |
| 冰镇果露 | −1 | +1 | −1 |
| 干爽草本 | +1 | −1 | −1 |
| 皮革烟草 | +1 | −1 | +1 |
| 蜜感白花 | +1 | +1 | −1 |
| 焦糖琥珀 | +1 | +1 | +1 |

**选了原型，冷暖与甜度就已经确定了。** 再单独问一遍是同一个信息问三次，
而且三次回答还能互相矛盾。

实测（150 组随机画像）：
- 「只答气质」vs「气质 + 手答冷暖甜度」top-10 重叠 **5.35/10**、top-1 换 **44.0%**
- 同一原型下，手答**一致**时总分 +20~22 分、手答**矛盾**时只 +10 分
  → 现状允许用户用 ②③ 把 ① 的结论推翻一半，而界面上只显示「你选的是 X」，看不出来

**改法**：新增 `deriveFromPreset(id)`，选原型时把结果写回 `state.answers`：

```js
temperature: c.dims.temp > 0 ? 'warm' : 'cool',
sweetness:   c.dims.sweet > 0 ? 3 : 1,
```

写回 `state.answers` 而不是改 scoring 接口，是为了让打分那条路径一行都不用动。
`temp` 不产出 `'neutral'`、`sweet` 不产出 2 —— 原型本身是二值的，
硬造中间值等于编数据。

副作用：这一屏原本 ① 占 7 张卡 + ②③ 各一排 + 两段 term-note，
在 390×844 下把「下一步」推到折叠线以下（visual 实测 +21.2px）。
