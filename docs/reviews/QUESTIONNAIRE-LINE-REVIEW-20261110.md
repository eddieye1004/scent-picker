## 1. 金标准草稿：画像可用，候选要重做

### 1.1 候选是知名度清单，不是 "推对了" 的答案

12 画像 × 5 候选 = 60 槽位，去重后只有 **36 瓶**。复用度：

| 出现次数 | 瓶 | 被哪几个画像共用 |
|---|---|---|
| **5×** | `creed-silver-mountain-water` | P01 P02 P05 P09 P11 |
| 4× | `creed-aventus` | P01 P05 P08 P11 |
| 4× | `mfk-aqua-universalis` | P01 P04 P05 P11 |
| 3× | `kilian-angels-share` | P01 P02 P03 |
| 3× | `byredo-gypsy-water` | P02 P05 P09 |
| 3× | `parfums-de-marly-layton` | P02 P05 P09 |

决定性证据是知名度分布。`data/perfumes.json` 的 `popularityRank`（数字越小越知名，553/1388 瓶有值）：

- 草稿 60 个槽位（有排名的那部分）：**中位 rank 37**
- 引擎六族 top10 实际选出的 37 瓶：**中位 rank 236**

草稿选的是「最有名的」，引擎推的是「最匹配的」。这两者不重合，是 P01/P06/P08 三个画像 top10 命中 0 的直接原因。

### 1.2 有两个候选违反自己的设定

| 画像 | 设定 | 候选 | 判定 | 证据 |
|---|---|---|---|---|
| P02 | `dislikedNotes=Jasmine/Tuberose/Orange Blossom` | `creed-silver-mountain-water` | **实锤违反** | `notesAll` 含 `Neroli`（= 橙花），与「怕晕白花」直接冲突 |
| P01 | `dislikedNotes=Vanilla` | `kilian-angels-share` | **存疑，非实锤** | `notesAll` = `Cognac, Oakwood, Cinnamon, Tonka Bean, Sandalwood, Praline`。**不含 Vanilla**；含 `Tonka Bean`（零陵香豆，香草近似物）。按字面不算违反，按体感算「怕甜的人可能不喜欢」。建议 P01 换掉，但理由要写成「甜度偏高」，不要写成「含香草」 |

P02 这一条尤其要命：这一屏的全部意义是「怕晕白花的人别给白花」，而候选里就有一瓶含橙花。

其余 10 个画像的候选在「家族 / 季节 / 避雷香调 / 避雷家族」四项硬条件上**无违反**。
`character=` 那几项也基本对得上（P04 全 5 瓶含 musky、P06 全 5 瓶含 resinous、P10 全 5 瓶含 leathery）。

> 我自己在这一条上差点犯错：第一遍探针把 `tonka` 当 `Vanilla` 的别名匹配，于是把 `kilian-angels-share` 判成「含香草」。复核原文后才发现 `notesAll` 里根本没有 Vanilla。**别名匹配可以当线索，不能当证据。**

### 1.3 草稿用的键名有两个引擎读不到

`docs/GOLD-STANDARD-DRAFT.md` 用了 6 个键：`family` `dislikedNotes` `season` `time` `character` `dislikedFamilies`。

`src/scoring.js` 实际读的是：
- `:288` `preferredTime: OCCASION_TIME[answers.occasion] || null` —— 读 `occasion`，**不读 `time`**
- `:296` `characterTags: Array.isArray(answers.characterTags) ? answers.characterTags : []` —— 读 `characterTags`，**不读 `character`**
- `:310` `character: answers.character || null` —— 这个读了，但只在 `:312` 当 `characterTags[0]` 的兜底

后果：**P09（只用 `character=herbal/green`）和 P10（只用 `character=leathery`）直接抛 `缺少 family 或 emotion`**，跑不起来。12 个画像里有 2 个不可执行。

`time=` 则静默失效 —— 不报错，也不会影响结果。

### 1.5 建议

候选不能由「知名度」筛。可行的替代口径（不需要跑现行打分，不违反 CONTROL 的禁令）：

1. **先用原始字段做硬约束筛**（`families` 含指定族 / `seasons` 含指定季节 / `character` 含指定气质 / `notesAll` 不含避雷词），得到一个池子（通常几十到几百瓶）。
2. **在池子里按 `popularityRank` 取前 5**，而不是全库按知名度取。
3. 人工从中**划掉明显不对的**，剩下的作为金标准。

`scripts/audit-gold.mjs` 已经在做这件事（我读了它的 header 和 PORTRAITS 定义），方向对。

## 2. CONTROL.md §3 第 2 步的两个候选方案：都有问题

CONTROL 给的方向是「打分改用主家族」或「命中计分按该瓶家族数衰减（如 1/√n）」。我离线各模拟了一遍。

### 2.1 方案 2a「只认主族」→ 引擎已经在这么做了，零效果

**代码事实**（`src/scoring.js:845-855`）：

```js
const isDominant = (s) => {
  const e = Object.entries(s.perfume.families || {})
    .filter(([k]) => k !== '_')
    .sort((a, b) => b[1] - a[1])[0];
  return !!e && e[0] === profile.family.id;
};
let ranked = scored;
if (profile.family) {
  const L1 = scored.filter(isDominant);
  const L2 = scored.filter((s) => wOf(s) >= 0.5);
  ranked = L1.length >= topN ? L1 : (L2.length >= topN ? L2 : scored);
}
```

「主族」的定义就是「按权重降序取第一个」，而这正是 `isDominant` 干的事。所以**方案 2a 要实现的东西，`recommend()` 里早就有了**。

实测六族入口下 top3 / top10 里非主族瓶的数量：

| 族 | top3 非主族 | top10 非主族 |
|---|---|---|
| citrus | 0 条 | 0 条 |
| floral | 0 条 | 0 条 |
| woody | 0 条 | 0 条 |
| amber | 0 条 | 0 条 |
| fresh | 0 条 | 0 条 |
| gourmand | 0 条 | 0 条 |

全零。方案 2a 一旦实施，就是把已有逻辑再写一遍，**输出逐位相同**。

> **本节我曾测错一次**：第一版把 recommend 的结果再按自己写的 `mainFam()` 过滤一遍，看到「3/3 重叠、完全不变」就下了结论。那个测试是同义反复 —— 我的 `mainFam()` 与 `isDominant()` 是同一个函数，过滤结果必然全 true。正确做法是直接查 `topN=10` 返回里有没有非主族瓶（上表）。结论没变，但论证换成了有效的那种。

顺带说明「家族稀释」为什么没吃掉区分度：家族因子吃的是**权重值**（`p.families[familyId]` 的 0–1 数），不是「有没有这个标签」。挂 5 个族的 Aventus 在 woody 入口下只拿 `woody: 0.5`，拿不满；只挂 1 族的 YSL Libre 拿 `floral: 1.0` 满分。惩罚已经内建在数据里了。

### 2.2 方案 2b「1/√n 衰减」→ 效果过大，且把长尾推到第一

离线把 top40 按 `分数 ÷ √(家族数)` 重排：

| 族 | top3 重叠 | top10 重叠 | top20 重叠 | 新 top1 |
|---|---|---|---|---|
| citrus | **0/3** | 5/10 | 12/20 | `tauer-perfumes-orange-star` |
| floral | 1/3 | 4/10 | 10/20 | `ysl-libre` |
| woody | 1/3 | 4/10 | 17/20 | `mancera-cedrat-boise` |
| amber | **0/3** | 2/10 | 10/20 | `khadlaj-icon` |
| fresh | 1/3 | 4/10 | 12/20 | `guerlain-jicky` |
| gourmand | 2/3 | 5/10 | 11/20 | `ariana-grande-cloud` |

`1/n`（更激进）的 top3 重叠是 0/3、1/3、1/3、0/3、1/3、2/3 —— 与 `1/√n` 几乎一样，说明这个改动对参数不敏感，影响是结构性的。

问题在于方向：新 top1 全是**冷门瓶**（Tauer Orange Star、Khadlaj Icon、Guerlain Jicky）。用户点「柑橘调」，推一瓶知名度排 700+ 的冷门小众，这不是改善。1/√n 把「家族标签挂得少」当成优点，但一瓶只挂 1 个族，往往是因为源站信息少，不是因为它更纯。

## 3. 我测出来的真问题（与 CONTROL 的三条不同）

### 3.1 真问题 A：家族因子饱和 —— 整族候选池几乎全部并列满分

口径：`topN` 设为该族 L1 池大小（这样 `L1.length >= topN` 成立，走的是真实路径），看池内家族项分值分布。

| 族 | L1 池 | 家族项满分（≥85） | 占比 | 池内不同总分档数 |
|---|---|---|---|---|
| **citrus** | 117 | **117** | **100%** | **22 档** |
| woody | 243 | 239 | 98% | 38 档 |
| floral | 533 | 402 | 75% | 68 档 |

**柑橘调最极端：117 瓶全部拿满 86 分，一棵树上吊死 117 个果子，靠剩下 49 分排座次。**
117 瓶只有 22 个不同总分，平均 5.3 瓶同分。前 10 名总分：

```
105.0  104.0  104.0  104.0  104.0  104.0  104.0  104.0  103.5  103.5
```

第 2 到第 8 名**全是 104.0**。这 7 瓶谁排第二、谁排第八，是数组遍历顺序决定的，不是匹配度决定的。

woody 池 243 瓶里 239 瓶满分（98%），前 10 名：

```
108.2  106.5  106.4  105.5  104.8  104.0  104.0  104.0  104.0  103.7
```

第 6–9 名并列 104.0。

**这就是「结果差强人意」的机制**：家族项（86 分）在整个族池内是常数，排序实际由气质 16 分 + 场合/浓淡/季节 33 分这 49 分决定。而气质的输入是七个二值原型 —— 见 §3.3，其中「冰镇果露」在 gourmand 入口下完全无效。

> **修正记录**：本节第一版用 `topN=1388` 统计，那个参数会让 `L1.length >= topN` 为假，从而降级到 L2（混入非主族瓶），测的是另一条路径。上表已用正确口径重算。方向没变，但柑橘族从「没测」变成「最严重」。

woody 前 15 名分数：`108.2 106.5 106.4 105.5 104.8 104.0 104.0 104.0 104.0 103.7 103.6 103.5 103.5 103.5 103.5`

全部 1388 瓶里只有 **173 个不同分值**，平均 8 瓶同分。这个粒度太粗。

**这一条才是「结果差强人意」的机制**：家族项在整族池内是常数，谁进 top3 取决于气质项那 16 分怎么分配，而那 16 分的输入是七个二值原型（§3.3）。

### 3.2 真问题 B：推荐结果的可达面窄，但库是完整的

**先说清一件事：1388 瓶全部在库里，也全部参与打分。** 没有任何一瓶被排除在推荐之外。
所谓的"触不到"是**排不进前十**，不是"没收录"。

| 本族内排名 | 瓶数 | 占比 |

真正要处理的是 §3.1 的饱和：同族 239 瓶并列满分时，进 top10 与否很大程度上是噪声，不是"更匹配"。

### 3.3 真问题 C：气质原型的分辨力不均

同一个族里换气质原型，top10 与新 top1 的变化：

| 族 | 最没区别的原型（≥9/10 重叠） | 最有力度的原型（≤2/10） |
|---|---|---|
| citrus | 无 | 雨后林地 1/10、蜜感白花 2/10 |
| floral | 冰镇果露 9/10、同 top1 | 雨后林地 2/10、**焦糖琥珀 0/10** |
| woody | 无 | 皮革烟草 1/10、蜜感白花 1/10 |
| amber | 无 | 蜜感白花 1/10、**焦糖琥珀 0/10** |
| fresh | 无 | 蜜感白花 2/10 |
| gourmand | 冰镇果露 **10/10、同 top1**、洁净清透 9/10 同 top1 | 雨后林地/皮革烟草 1/10、**蜜感白花 0/10、焦糖琥珀 0/10** |

**两个原型形同虚设**：

- `冰镇果露` 在 **gourmand 入口下完全不改变结果**（10/10 重叠、同 top1）。它的 tags 是 `{fruity:3, sweet:2, citrusy:1, floral:1}`，与美食调族的固有气质高度重合 —— 选了等于没选。
- `洁净清透` 在 gourmand 下 9/10 重叠且同 top1，同样接近失效。

这与我们 v37 修掉的「intensity 5 档里 3 档等于没答」是同一类缺陷，只是发生在气质层。**6 族 × 7 原型 = 42 种组合里，至少 2 个是死选项。**

反向的极端也存在：`焦糖琥珀` 在 floral 与 amber 下是 0/10（top10 全换），`蜜感白花` 在 gourmand 下也是 0/10。说明气质层不是"普遍无力"，而是**分布极不均** —— 有的原型几乎不做事，有的原型改写整个榜单。

### 3.4 气质标签稀疏：CONTROL 的数字对，但后果被高估

所以「五个稀疏标签」里，`salty` / `rich` / `balsamic` 三个根本没被任何气质原型使用，改了也不影响推荐；真正要处理的只有 `leathery` 与 `clean`。

## 5. 给打分线的具体建议（按优先级）

0. **【最高优先】修 `recommend()` 的返回顺序不单调 —— 这是用户直接看得见的 bug，零风险。**
   `scoring.js:861-888` 的多样性三轮是 `picked.push()` **追加**，不是重排；三轮跑完后直接 `return picked`，没有按分数再排一次。结果：分数高的瓶可能排在分数低的瓶后面。
   实测 woody 入口（只答第 1 步）：

   第2张 armaf-eter-desert-breeze     95.4   ← 比第 3 张低 11 分

### 5.1 排序错乱的成因：族名去重几乎不起作用

`familySource` 在每族的 L1 池里只有 1–4 种取值：

| 族 | L1 池 | `familySource` 种数 |
|---|---|---|
| citrus | 117 | **1**（Sunlit Citrus） |
| gourmand | 142 | **1**（Velvet Sweet） |
| woody | 243 | 2（Wood & Root / Oud Court） |
| amber | 191 | 3 |
| fresh | 162 | 3 |
| floral | 533 | 4 |

`seenFamily` 这层去重在 citrus 与 gourmand 里等于不存在 —— 所有瓶同源族。剩下的只有品牌去重，而品牌去重一旦命中，就把该瓶挤到后面，靠第二轮「放宽家族」补回来，于是顺序乱了。

这也是为什么 citrus/gourmand 的 top3 会出现 **第 2、3 名并列同分**（`105.0 104.0 104.0` / `104.1 104.0 104.0`）：本来就是一串同分瓶，谁前谁后取决于品牌去重先碰到谁。
