## 一、五处证据冲突的裁定

### C-1 基线状态：「已提交且全通过」vs 干净 HEAD 崩溃

| 口径 | 主张 | 实测 |
|---|---|---|
| 上轮自述 | 缺陷修复已完成、测试全通过、已提交 | 工作区确实全绿（295 项） |
| 干净导出 HEAD | — | `test-render.mjs:651` 抛 `TypeError: MARKS[id] is not a function`，第 651 行之后 60 余条断言一条未跑 |

**结论：以「干净导出 HEAD」为准。** 理由：`git status` 只显示「还有文件没提交」，这不构成「测试全通过」的证据 —— 它证明的是工作区状态，而交付物是那个提交。我的自述当时混用了两个口径。

**处置**：已修（D48 把 taxonomy v2.0.0 提交完整），并新增 `scripts/check-head.mjs` 把「干净导出跑测试」变成一条命令，判据固化为「断言数不得低于基线」。已实测：未提交 3 条新断言时它准确报 `PASS 145 < 基线 148`。

### C-3 390 命中区：39×26 vs 分状态合格/不合格

| 状态 | 实测（390 视口） | 是否达 44×44 |
|---|---|---|
| 闭合态 `.lvl1` | 56×44 | ✓ |
| 展开态 `.lvl1` | **39×26** | ✗ |
| `.lvl2` | 77×37 | 高不足 44 |

**结论：以分状态实测为准。** 理由：评审只测了展开态就下结论「不适合触屏」，这个结论对闭合态是错的；反过来，只说「合格」也不对。两个状态命中区不同，是因为展开态要给中圈让位。

**更优选择：修展开态，不动闭合态。** 理由：闭合态已达标，改它纯属浪费；展开态 39×26 确实点不中，加一层透明命中垫即可（视觉零变化）。已列为 P2-6。

顺带一提 `.lvl2` 是 77×37 —— **宽度够、高度不够**，比 `.lvl1` 展开态好修（只需加 7px 垂直内边距或命中垫）。

### C-4 「中圈保留 7 段谱」vs taxonomy v2.0.0 花香族只 6 类

| 口径 | 内容 |
|---|---|
| 原始要求（m00001 第③条） | 完整保留中圈 7 段谱的 UI 结构/样式/交互 |
| v2.0.0 现状 | 六族分别是 4 / **6** / 6 / 6 / 4 / 2 类，**没有任何一族是 7 类** |

**这是唯一需要你拍板的一项**，因为两种解读指向完全相反的动作：

| 解读 | 含义 | 需要做什么 | 代价 |
|---|---|---|---|
| **A（建议）** | 「7 段谱」指**分段结构**（一圈等分弧段 + 标签正立 + 进出场编排），段数由数据决定 | 什么都不用做，已满足 | 0 |
| B | 字面要求「每族 7 个类」 | 回退 taxonomy v2.0.0，恢复 32 类 | 丢掉整轮分类审计成果；v2 的合并正是为了消除「黄花×白花重叠 77%」这类伪类 |

**建议取 A，理由三条**：
1. 原始要求的下半句是「结构/样式/交互」，不是「数量」。三样里没有一样依赖 7 这个数。
2. `buildWheel` 的等分逻辑本来就是按 `f.subfamilies.length` 算的，段数变化是设计内行为 —— 代码从未假设过 7。
3. v2.0.0 的 28 类是**审计过的结论**（32 类里只有 4 类同时满足互斥/同质/可辨），为凑 7 段回退等于用一个数字推翻一轮数据工作。

**如果你要 B**：请明确说「回退到 32 类」，我按 `backup-before-deadcode` 那条线恢复 taxonomy 与图标，其余改动保留。

## 二、工作区与 Rules 的处置方案（供你选定）

当前状态：`data/taxonomy.json` = v2.1.0（未提交），`_audit/` 有 4 个已修改 + 11 个未跟踪文件。

### 方案 A · 提交 v2.1.0 并记 D50（推荐）

| 维度 | 内容 |
|---|---|
| **做什么** | 把 taxonomy v2.1.0 + `_audit/` 下规则相关文件一起提交；`rules-v1.cjs.bak` 与 `colored-legacy.html` 等过程产物按 `.gitignore` 惯例排除或一并入库（需你定） |
| **影响面** | taxonomy 只加字段，无消费方 → 运行时行为零变化；四套测试已在 v2.1.0 下跑过全绿 |
| **好处** | 工作区立刻干净；v2.1 的 `boundary`（判别特征/排除条件/典型示例）是**接入打分的前置数据**，入库后 P1-5 才有得用 |
| **风险** | 若这份 rules 是实验性草稿，入库会给人「已定稿」的错觉。**缓解**：commit message 与 D50 明确写「数据层已入、打分未接」 |
| **前提** | 你能确认它至少是「想留下的」 |

### 方案 B · 只提交 taxonomy，`_audit/` 进 gitignore

| 维度 | 内容 |
|---|---|
| **做什么** | 提交 `data/taxonomy.json`（v2.1.0）；把 `_audit/` 加进 `.gitignore`，下次清理时归档到仓库外 |
| **影响面** | 与 A 相同的运行时零变化 |
| **好处** | 仓库只留交付必需物；`_audit/` 是 244KB 的过程证据，不进仓也不影响复现（`scripts/` 里的测试自成体系） |
| **风险** | 丢掉「结论的可追溯性」—— v2 的合并/拆分凭据就在 `_audit/`，删了以后无法回答「为什么把黄花并入白花」 |
| **前提** | 你更在意仓库轻量，且接受审计链离开 git |

### 方案 C · 全部还原到 HEAD

| 维度 | 内容 |
|---|---|
| **做什么** | `git checkout -- data/taxonomy.json`，`rm -rf _audit/` 未跟踪部分（先打包到仓库外） |
| **影响面** | 回到 28 类 + 无 rules 的 v2.0.0 |
| **好处** | 工作区与 HEAD 完全一致，最干净 |
| **风险** | **丢掉 v2.1 的 boundary 数据**。若那是外部进程花时间做的，重做成本未知 |
| **前提** | 你确定这份 rules 不要了 |

### 我的建议：**A**

理由：v2.1.0 只加字段、不改结构、测试全绿，「留着它」的边际成本接近零；而 `boundary` 是 P1-5（把分类审计收益接进推荐打分）唯一的输入。选 C 会让 P1-5 无从下手。

**唯一需要你回答的**：那份 `_audit/apply-rules.cjs` 是你（或另一个 agent）有意做的吗？
- 是 → 走 A
- 不确定 → 走 B（保 taxonomy、弃过程文件）
- 不要 → 走 C
